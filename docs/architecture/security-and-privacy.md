# Security & privacy

> This document describes technical measures. It is not legal advice; lawful-basis rules (especially for legitimate interest and ePrivacy) must be validated with a privacy professional per jurisdiction.

## 1. GDPR by design — mapping

| GDPR / ePrivacy requirement | Platform mechanism |
|---|---|
| Lawful basis (Art. 6) | **Consent & lawful-basis ledger** per profile × purpose × channel; every message/journey declares a purpose; send gateway enforces |
| Legitimate interest | Purpose configured with basis `legitimate_interest` + linked **LIA record** (assessment text, owner, review date); right to object always honoured and recorded |
| Email marketing under LI (ePrivacy Art. 13(2) "soft opt-in") | Policy template: only existing customers, similar products, opt-out offered at collection and in every message (one-click unsubscribe mandatory) |
| Cookies / tracking consent (ePrivacy Art. 5(3)) | SDK: no non-essential storage/tracking before consent; TCF / Consent Mode / custom CMP signals; cookieless mode |
| Data minimization (Art. 5) | Tracking plan with allowed properties; attribute schema with PII classes; IP truncation; drop-unknown option |
| Storage limitation | Retention per data class: ClickHouse TTL, Postgres retention jobs, profile inactivity expiry |
| Right of access / portability (Art. 15, 20) | DSR command: export profile, identifiers, consent history, events, messages as JSON/CSV |
| Right to erasure (Art. 17) | DSR erasure: delete profile rows, **crypto-shred** per-profile key, ClickHouse delete by identifiers, delete browser/app push subscriptions, suppression-hash kept to prevent re-contact (documented exception); restores replay erasures recorded after the snapshot so an erased person does not come back |
| Records of processing (Art. 30) | Purposes, sub-processors (ESPs, LLM providers), data categories configurable and exportable |
| Security of processing (Art. 32) | Encryption at rest/in transit, RBAC, audit log, see below |
| Automated decision-making (Art. 22) | AI decisions limited to marketing content/timing; logged with rationale; `ai_processing` purpose can be disabled per profile/workspace |
| Data residency / transfers | Self-hosted: where you run it. LLM/ESP providers flagged with region; EU-only provider policy option |

## 2. Consent & lawful-basis ledger

```
purposes(workspace_id, key, name, basis: consent|legitimate_interest|contract|legal_obligation,
         channels[], lia_id?, requires_double_opt_in, description)
consent_records(workspace_id, profile_id, purpose_key, channel, status: granted|denied|withdrawn|objected,
                basis, source (form, sdk, import, api, unsubscribe link), proof jsonb (ip-trunc, ua, text-version, double-opt-in token),
                recorded_at, recorded_by)        -- append-only
consent_state(workspace_id, profile_id, purpose_key, channel, effective_status, updated_at)  -- materialized
suppressions(workspace_id, channel, value_hash, reason, at)  -- survives erasure (hash only)
```

The current status of a purpose combines the all-channels row (`''`) and the channel rows by one rule, [ADR-0014](adr/0014-consent-channel-precedence.md): for a channel, the newer of `''` and that channel; without a channel (segments, audience syncs), a newer refusal on any channel wins.

Evaluation in the send gateway: `consent` basis → needs `granted`; `legitimate_interest` → allowed unless `objected/withdrawn`, and the LI policy conditions hold (e.g. `is_customer` trait for soft opt-in). Double opt-in flows are built-in journeys.

## 3. Encryption & keys

- **In transit:** TLS everywhere, terminated by the operator's proxy or tunnel in front of the app (see [compose.md](../deployment/compose.md) and [kubernetes.md](../deployment/kubernetes.md)); internal connections TLS-capable.
- **At rest:** rely on disk/volume encryption for the base layer, plus **application-level field encryption** for PII:
  - Envelope encryption: a **KEK** from a pluggable key provider (env/file for small installs, AWS KMS, GCP KMS, OpenBao/HashiCorp Vault transit) wraps **DEKs**.
  - **Per-profile DEK** for PII fields in Postgres and ClickHouse (`properties` PII fields). Erasure = delete the DEK → data in events and **backups** becomes unreadable (crypto-shredding).
  - Lookup via HMAC hashes (`value_hash`) so matching doesn't need decryption.
- **Secrets** (ESP keys, LLM keys, OAuth tokens, webhook secrets): encrypted with workspace DEK, write-only via API, key rotation command in CLI.
- BYOK/customer-managed KEK for SaaS: later phase, already enabled by the key provider interface.

**Erasure tombstones (#210).** An erasure keeps one tombstone per identifier of the person: an HMAC-SHA256 hash keyed with the workspace's matching data key, never the raw user id, e-mail address or phone number. For `ERASURE_GRACE_HOURS` (24 by default, configurable; with `0` only events from before the erasure are dropped) after the erasure, an event that names only erased identifiers and happened before that window is dropped by the resolver instead of creating a new profile, so events already on the bus, SDK retries, offline queues or late provider webhooks cannot recreate the person. After the window, new activity is treated as a new person, and the hourly retention job deletes tombstones once the window plus seven days has passed.

**Erasure cleanup and in-flight writes (#978, mitigation).** `profiles.erase` commits the SQL deletion first; a durable scheduler job then sweeps ClickHouse and the hot-state snapshot. The sweep is two-phase. The first successful ClickHouse delete records `first_sweep_done_at`; a final delete is scheduled at least `W = CLICKHOUSE_REQUEST_TIMEOUT_MS (30 s) + 5 s` after that checkpoint, and only after it does the job report `complete`. `W` is the mitigation's scheduling interval between sweeps. It is **not** a proof that a write has finished: a client request timeout does not prove the ClickHouse server stopped executing, and an eligibility check can run before the erasure and write afterwards. Every person-linked insert (`events`, `message_events`, `journey_events`) sets `async_insert=0`, so a resolved insert reflects ClickHouse's response, but a timeout is not proof that server-side work ended. The ClickHouse sink filters events against the erasure tombstones before every insert, with the same identifier hashes and grace window as the resolver; like the resolver, it drops an event only when none of its identifiers resolves to a live profile, so an erased visitor's device id on a live person's event does not discard that person's event. The event store also drops journey and message-event rows for a profile that no longer exists.

This was the **0.15.3/0.16 mitigation, not a general “nothing can reappear” guarantee**. A write that was already in flight at the ClickHouse server, or an eligibility check that ran before the erasure but whose write lands later, could still insert a row after the final sweep. 0.17.0 (#1037) activates read-time exclusion so such rows are invisible to every query; the double sweep remains a physical cleanup step, not the correctness boundary.

**Erasure-key ledger and subject keys (#1037, 0.17.0 part 1).** The erasure's SQL transaction writes one row per covered identifier to `erasure_keys`. A dedicated, workspace-scoped **exclusion key** (data-key purpose `exclusion`) hashes every value as `HMAC_exclusion(kind, normalised value)`; it is domain-separated from the matching key, wrapped by the KEK like other data keys, and never sent to ClickHouse. `am rotate-keys` only re-wraps it with the KEK (its id and hashes do not change), and rotating the matching key does not affect it. `key_version` records the exclusion key id on every value.

Covered kinds: the whole merged profile family (`profile`), the anonymous and user ids stored rows carry (`anonymous_id`, `user_id`), an alias's `previousId` (`alias_previous_id`), the supported ad click ids the click-id hook attaches to a person (`gclid`, `gbraid`, `wbraid`, `fbc`, `fbp`, `msclkid`, `li_fat_id`, `ttclid`, `ttp`, `epik`), and e-mail/phone (`email`, `phone`). E-mail and phone are hashed from the normalised address or number, not from the matching-key lookup hash, so a matching-key rotation cannot change them. Nothing is stored raw: not in the ledger, not in ClickHouse `erased_subjects`, not in the subject columns, and not in the restore capture.

**Supported-identity policy.** A value is excluded only if it was stored as one of those subject keys. Free-form identifiers in event properties, connector- or vendor-specific ids without a subject column, and externally supplied device ids other than the anonymous id are **not** subject keys and remain visible to queries until a later PR decides their coverage. Historical rows have two known gaps: the event store never kept e-mail/phone traits, and it did not store an alias `previousId` before this release, so an alias row written earlier can only be matched by its own ids (and by a click id in its context). Those rows get `ids_only` coverage rather than being reported as fully covered.

ClickHouse gains an `erased_subjects` table (`workspace_id`, `kind`, `key`, `key_version`, `erasure_id`, `generation`, `recorded_at`), unpartitioned and replaced by the monotonic `generation`, so a replay can never regress a newer exclusion and no month partition decides identity. Its publish function is idempotent. Person-linked rows in `events`, `message_events` and `journey_events` gain defaulted subject-key columns filled by the writers, plus `subject_coverage`: `full` when the writer saw every applicable identifier (including an alias `previousId` and e-mail/phone traits), `none` when it wrote nothing. Historical rows are never rewritten. A scheduler job reads each workspace's uncovered rows, hashes the ids those rows still store in the application (the key never reaches ClickHouse), and writes the result to a side table keyed by each row's complete replacing key without `workspace_id` (events: `name`, `anonymous_id`, `timestamp`, `event_id`; message events: `message_id`, `type`, `event_id`; journey events: `journey_id`, `participant_id`, `seq`, `type`) with coverage `ids_only` or `none`. Protected reads (PR 2) use `coalesce(nullIf(row.subject_*, ''), side.subject_*)` only when the row's coverage is not `full`, so a complete concurrent redelivery can never be superseded by a stale copy. The side table is `ReplacingMergeTree(version)` with a monotonic version. A pass is complete only when a FINAL count of rows lacking coverage in both the row and the side table is zero; the cursor is reset whenever the forward scan ends (even with a positive count), and the job revalidates at a low frequency, so a legacy row that lands later is still found. `am doctor` reports the remaining count, which PR 3 reads before activation; because the count costs three FINAL joins per workspace under a three-second budget, a check that cannot finish reports **unknown**, never zero. Every person-linked insert stays synchronous (`async_insert=0`), and a guard test fails if a writer omits it.

A legacy e-mail or phone identifier whose sealed plaintext can no longer be opened (for example a pre-upgrade row without `value_enc`) has no recoverable write-time value. The ledger records that identifier with `coverage = 'unavailable'` — the stored matching-key value is kept only as an explanatory placeholder — instead of publishing a hash that could never match. An erasure with such a row can still complete: its status reports `exclusion: 'partial'` and lists the affected kinds in `unavailableKinds` rather than implying that the address or number was excluded. Every identifier whose plaintext is recoverable is excluded normally.

**Exclusion key lifecycle.** The exclusion key is long-lived and is **not** rotated with the matching key. `am rotate-keys` only re-wraps it with the KEK, leaving its id and hashes unchanged. If the key is ever compromised, a new `exclusion` key is minted for new writes and new erasures, while the old wrapped key is **kept indefinitely**: ledger HMACs cannot be recomputed after the subject's crypto-shredded plaintext is gone, and historical subject columns were hashed with the old key. Ledger rows and subject rows record `key_version`, and protected reads check every retained version. Compromise exposes only pseudonymous linkage of hashed identifiers (an attacker with the key and a candidate identifier can confirm a match); it cannot be revoked for entries already written, which is why the key must be protected like the matching key. The ledger and the wrapped exclusion keys travel with the restore capture, and a replay activates the key the ledger references — never a second active key for a workspace that has ledger rows.

The read path in 0.17.0 routes every person-linked read through protected views and publishes exclusions before an erasure reports complete; the maintenance credential those reads use must be exempt from the existing `TO ALL` ClickHouse row policy.

**Erasure-safe restores (#144).** Crypto-shredding cannot scrub a backup taken before the erasure: that snapshot still holds the profile key and the encrypted personal data. `am restore` therefore reads the `erasures` and `erasure_tombstones` rows from the live database before replacing it and replays them after the Postgres load. For each erasure it deletes the profiles and identifiers again (with profile keys, consent records, messages, journey participations and segment memberships), deletes the person's browser/app push subscriptions by anonymous id and user id (0.5.2), restores the e-mail and phone suppression hashes, and re-inserts the erasure row and its keyed tombstones. Replay is idempotent and tolerates profiles the snapshot no longer has. `BACKUP_KEEP_DAYS` (14 by default) is the documented maximum age of a restore point, and therefore the window in which a snapshot can predate an erasure; a remote lifecycle must not outlive it. A restore whose erasure log cannot be read stops rather than proceed. `--clickhouse` reloads event rows as exported; the per-profile key is still destroyed by the replay, so sealed personal data stays unreadable, but a DSR that must remove event rows needs a ClickHouse snapshot taken after the erasure.

**Read-time exclusion (#1037, protected reads).** 0.17.0 makes an erasure's exclusions part of the read path, so a row that lands after the sweep is still invisible. The pieces:

- **Durable publication.** An erasure's SQL transaction writes the `erasure_keys` ledger (part 1). The cleanup job publishes those rows to ClickHouse's `erased_subjects` *before any sweep*, under a new monotonically increasing per-workspace generation (`erasure_generations`), and records `published_generation`/`published_at` on the job only after a `FINAL` read confirms every key is visible. Publication is idempotent; a retry takes a higher generation. `am restore` reconciles the **restored** ledger with `erased_subjects` as its last step, after every ClickHouse load: it re-inserts the missing full-coverage keys in batches, confirms them visible, and only then marks the jobs published (#1194). That covers a Postgres-only restore, an older `--clickhouse` file, both, and a fresh target whose dump already carried a completed job; a completed job is not reopened for another sweep, and an unfinished one is queued for its remaining sweep. The reconciliation runs per workspace with `app.workspace_id` set, so a restore run as a non-BYPASSRLS table owner (where FORCE RLS hides the ledger) still reads it, and it removes the outbox rows naming an erased profile that the job's final worker pass would have removed. `am restore` takes one exclusive session advisory lock for its whole run (a second restore, `--clear-fence` or any server start is refused), and every server process and `am migrate` takes that lock **shared on a dedicated connection before its first migration, holding it until shutdown**. It also raises a fence row in `public.restore_fence` — a table every dump excludes, so `pg_restore --clean` cannot remove it — **before** replacing Postgres. The fence is cleared only after reconciliation, and a server refuses to start while it exists or while a restore holds the lock (and exits if its own lock connection is lost), so an erasure reported complete before the backup is never readable again even when `pg_restore` commits and then fails. `profiles.erasureStatus` reports it pending until that publication is confirmed.
- **Protected views.** `events_protected`, `message_events_protected` and `journey_events_protected` are parameterized ClickHouse views over the base tables, invoked as `events_protected(ws={ws:UUID})` with the workspace the caller is already reading. Each one dedupes its replacing table (`FINAL`) and removes a row when any subject key matches an `erased_subjects` row of the same workspace, before any aggregation. Subject keys are the row's own columns when `subject_coverage = 'full'`; otherwise they are coalesced with the `subject_key_backfill` side entry, so a historical row that was never rewritten is still excluded. The match is on the key value alone: every key is `HMAC_exclusion(kind, value)` under the workspace exclusion key, and every retained `key_version` stays valid. A row that is neither complete nor backfilled is **unverified**: a workspace with published exclusions removes it instead of treating its missing keys as a non-match (#1195). That is what keeps a legacy-shaped row — an undrained pre-0.17.0 writer, a restored pre-0.17.0 table, manual SQL — invisible when it names an erased person and lands after the coverage gate recorded zero. The rule is gated on the workspace having at least one published exclusion, so a publication that is still in flight does not hide data it could not exclude yet. It is counted by `am doctor`'s `clickhouse.subject-keys` check, and the completion gate refuses to mark an erasure complete while the count is non-zero.
- **Fast path.** A workspace with no durable erasure ledger has nothing to exclude, so the shared read layer (EventStore, the analytics compiler, the pending-outbox union, campaign identity, warehouse exports and ad attribution) reads the base table directly: same SQL, same plan, no ledger scan. The decision is the committed `erasure_keys` ledger per request — written in the erasure's own SQL transaction — not a worker-allocated generation, so an erasure recorded by an older release or restored from a snapshot already takes the protected path even though its publication has not run. Only a "yes" is cached (in a bounded LRU; `erasure_keys` is never pruned, so "yes" cannot become false) and a "no" is always answered by the database, so a later erasure takes effect on the next read. A failure to read the ledger is fail-closed, reported once and rethrown explicitly. At startup the scheduler re-enqueues every erasure whose ledger has publishable rows but no recorded publication, so erasures completed before this release, or restored from an older snapshot, get their `erased_subjects` rows too — a job that is still running keeps its claim, so the pass never resets work in flight.

  Between the erasure's commit and its publication, the protected view has no exclusion rows yet: the read already takes the protected path, but it still returns the subject until the cleanup job has published the ledger to `erased_subjects`. Exclusion therefore takes effect at publication, not at commit. That is the deliberate ordering for the completion contract: a workspace's erasure is only `complete` (part 3) once the publication is confirmed visible, so no caller is told the erasure finished while a read can still see the person.
- **Bounded exclusion shape.** A protected view builds the workspace's ledger as one set per query (`IN (SELECT …)` captured once, never per row) and tests the row's at most sixteen subject keys with a single `arrayExists`. An id-scoped read — a broadcast or journey guardrail, or a message-stat read — bounds that set further, to the subject keys its own messages can carry, and derives the bound **inside the counting statement** rather than from an earlier read, so a message committed between the two is still excluded; an empty scope still runs the predicate. The send path therefore does not pay for a workspace-wide ledger. That shape replaced two earlier ones: a `groupUniqArray` joined onto every row, which requested 10.13 GiB with 100,000 exclusions, and one anti-join per kind, which was correct but added sixteen joins to every read. Both ledger and backfill scans name `workspace_id = {ws:UUID}`, so they use their tables' ordering prefixes; the backfill identity join is additionally fed by runtime filters built from the base rows. Benchmarks pin memory and latency: `packages/events/test/protected-reads-benchmark.test.ts` (1.2M events, 12 workspaces, a 100,000-key ledger, a 1 GiB per-query limit) and `packages/analytics/test/protected-reads-latency.test.ts` (the five reader paths, as base / fast-path / large-ledger ratios).
- **Every reader is routed.** EventStore reads, `analytics.query`, the named reports, campaign measures and summaries, alerts, segments (event and engagement conditions), journeys, campaign identity and warehouse exports read the views. Both halves of a pending-outbox union are filtered: the published half by the view, the queued snapshot by the same keyed hash computed in the application. Ad spend (`ad_spend`, campaign-level) is exempt, because it names campaigns, not people.
- **Maintenance keeps the base tables.** Inserts (the sink), erasure sweeps, the subject-key backfill and migrations are the only writers/readers of the base tables. `packages/events/test/protected-reads-guard.test.ts` fails if any other source file names one after `FROM` or `JOIN`. A dedicated ClickHouse user that may `SELECT` the views but not the tables is the deployment-level half of this; the application currently talks to ClickHouse as one configured user (`CLICKHOUSE_URL`), so this release enforces the split in code and the guard, and leaves the credential split as the documented next step. The `erased_subjects` row policy stays `TO ALL` for the same reason: there is no second user to exempt yet.
- **Caching.** The 60-second analytics result cache is keyed by a workspace's confirmed-publication epoch (`erasure_generations.visible_publications`), which moves only after a publication's `FINAL` visibility check. It cannot key on the publication generation: a generation is allocated before its rows reach ClickHouse, so a query that ran during the insert would cache the pre-exclusion answer under the new value and keep serving it for up to a minute. Every confirmed publication moves the epoch, so concurrent publishers are safe.

Completion semantics are now the contract. `profiles.erasureStatus` reports **logical completion** only when the erasure's ledger is published and confirmed visible in `erased_subjects` *and* the workspace's subject-key coverage count is zero: no person-linked row remains that a protected read cannot check. A job that cannot satisfy the gate stays `pending` or `running` with a `reason` (`publication`, `outbox`, `final_sweep` or `subject_key_coverage`); the SQL completion carries the same gates. Once complete, every application query started afterwards excludes the erased subject, including rows written later; a legacy-shaped row that the backfill has not covered yet is not returned at all (#1195). **Physical deletion is a separate, eventual milestone**: `purge: { state, lastSweepAt, deletedRows }` reports it, an erasure can be logically complete while its purge is still pending, and the scheduler re-sweeps at a low frequency because late writes keep arriving. The recurring purge matches the same keyed subject values (including `events.profile_id` through its exclusion hash or the identity-keyed backfill entry) in bounded batches, never deletes the ledger or published exclusions it needs, and is fenced per workspace. It also deletes the matching `subject_key_backfill` side entries: those rows are keyed by the raw identity (name, anonymous id, timestamp, event id), so once the base row is gone the side entry would otherwise be the last raw trace of the erased person. Because the ledger deliberately covers the supported click-id kinds (`gclid`, `gbraid`, `wbraid`, `fbc`, `fbp`, `msclkid`, `li_fat_id`, `ttclid`, `ttp`, `epik`), a row matching a shared click id of an erased person is **physically deleted even when the row also names a live person** — read-time exclusion has already hidden it, and physical deletion follows the same owner-approved ledger semantics rather than leaving the shared identifier behind. `am doctor` reports exclusion coverage (`privacy.erasureExclusion`, including unavailable kinds) and the physical purge backlog (`queue.erasurePurge`) separately: an empty cleanup queue alone is not evidence that rows are gone.

## 4. Identity, authentication & authorization

- **Auth:** Better Auth (MIT) — email/password, the MCP OAuth 2.1 authorization server, per-workspace OIDC/SAML single sign-on and SCIM 2.0 provisioning. No organization, passkey or TOTP/2FA plugin is enabled.
- **Principals:** `user`, `agent` (owned by a user/workspace, scoped tokens), `service` (SDK write keys, server keys, connectors).
- **Authorization:** RBAC with built-in roles (owner, admin, marketer, approver, viewer) mapping to permission strings checked in the command layer; per-agent scope sets. Designed so it can move to relationship-based authz (OpenFGA, Apache-2.0) if fine-grained sharing is needed.
- **Tenant isolation:** `workspace_id` + Postgres RLS (session variable set by the command layer); ClickHouse row policies; NATS subjects per workspace; Valkey key prefixes.
- **Audit log:** append-only, hash-chained table of every command (principal, effect, input hash, result, ip, user agent), exportable; separate from analytics.
- **Password reset (#191):** the public request path is account-agnostic: every syntactically valid normalized address is sealed with a purpose-separated key derived from `AUTH_SECRET` and inserted once into the durable `password_reset_deliveries` queue, with no account lookup, token mint, tenant data key or provider I/O. The worker resolves the account, re-checks eligibility, mints Better Auth's single-use 45-minute token (stored hashed in `verification`), sends it with bounded retries and wipes the sealed address/token. Known, unknown and single sign-on addresses therefore do the same request work; the neutral answer and response timing do not depend on account existence or a provider delay. Enforced single sign-on domains and SSO/SCIM accounts without a password get no mail, including when that changes after the request was queued. Unprocessed rows expire and are wiped after 24 hours; terminal rows are pruned after 7 days by the worker. Delivery is at least once (a crash after provider acceptance can resend). A successful reset revokes every session of that person. Requests and resets are rate limited per IP and per address in Valkey (shared by all workers); a limiter outage returns a uniform 503 before enqueueing or forwarding. Request outcomes and resets are audited with person, IP and outcome, never the address, token or password ([identity.md](../identity.md#password-reset-191)).

## 5. Application security controls

| Threat | Control |
|---|---|
| SSRF via webhooks / HTTP nodes / connector URLs | Egress proxy or resolver guard blocking private/link-local/metadata ranges; per-workspace allow-lists |
| Template injection | LiquidJS sandbox (no filesystem, no code), output escaping by default, render time & loop limits |
| Prompt injection via profile/event data reaching LLMs | Data is passed as clearly delimited data, LLM outputs are schema-validated and can only choose among configured options; AI nodes cannot call platform tools in v1 |
| Malicious MCP/agent behaviour | Scopes, drafts + approvals, the policy engine (audience threshold, per-agent limits, the autonomy switch), pausing an agent, AI budgets, the send gateway, the action ledger and audit ([agentic-autonomy.md](agentic-autonomy.md)) |
| Abuse of public write keys | Origin allow-list, rate limits, schema validation, payload size limits, bot filtering |
| Abuse of public signup forms | Origin allow-list, a per-form and per-client token bucket in Valkey shared by every replica (an unreachable store refuses with `rate_limit_unavailable` rather than allowing an unbounded local fallback), a honeypot, optional Turnstile, body limits |
| Account enumeration and mail flooding via password reset | One neutral answer for every request, per-IP and per-address token buckets in Valkey, a cooldown per address, single-use tokens that expire, audit entries that never carry the token |
| XSS in editors/experiences | CSP, sanitization of experience HTML in the browser SDK (`packages/sdk-js/src/personalize.ts`), a bounded htmlparser2 allow-list for hosted archive bodies and uploaded SVGs, editors in sandboxed iframes where possible |
| Supply chain | Lockfile, Dependabot, dependency review, `pnpm audit`/OSV scanning, SBOM and build-provenance attestations on the release image and files, minimal base images |
| Custom code steps (later) | Not in v1. If added: isolated runtime (separate sandboxed process / WASM) with no network by default |
| Secrets leakage | Never returned by APIs, redacted in logs/traces, secret scanning in CI |

The egress guard normalises the IPv6 forms that embed an IPv4 address (IPv4-mapped `::ffff:0:0/96`, IPv4-compatible `::/96`, NAT64 `64:ff9b::/96` and 6to4 `2002::/16`) and applies the IPv4 block list to the embedded address, both to literals and to DNS answers at connect time; the Postgres warehouse destination resolves once and pins the validated address. Outbound HTTP requests stop reading as soon as the response byte limit is crossed and use a total deadline covering connect, headers and body, so an oversized or slowly trickled response cannot keep a worker and connection open.

**Request body limits.** Public and API POST bodies are bounded before they are parsed or buffered, counting encoded bytes rather than JavaScript string length. An oversized declared `Content-Length` is refused before the body is touched; every other body is counted in bytes as it streams in and refused as soon as it crosses the limit, so an understated length or a chunked request without one cannot slip past the guard and an oversized request never sits in memory in full. The ingest gateway allows 500 KB per batch, inbound webhooks 1 MB (checked before the secret URL is authenticated), public forms 64 KB, the decision API 32 KB, preference-centre and SMS webhook POSTs 64 KB, REST commands 1 MB (`assets.upload` keeps its larger `ASSET_MAX_BYTES`-derived limit), the MCP endpoint 1 MB and the generic Better Auth `/api/auth/*` catch-all 256 KB. The SAML ACS and SLO callbacks have their own ceiling, derived from the 262,144-byte `SAMLResponse` limit plus worst-case form encoding. All answer `413 Payload Too Large`.

## 6. Operational security

- Backups: `am backup` writes Postgres (`pg_dump -Fc`) and optional ClickHouse Native files with `0700` directories and `0600` files, but it does **not** encrypt them. Put `BACKUP_DIR` on an encrypted volume or host (LUKS, ZFS encryption, an encrypted disk or object bucket) and copy backups only to an encrypted destination; an encrypted volume protects a lost disk, not a backup copied to a share. `.env` and `MASTER_KEY` stay outside the backup. The manifest records which key the backup needs (a provider reference and a sealed check value, never the key), and `am restore` refuses a wrong key before replacing Postgres. `am backup --verify` re-hashes every file and reads the dump's table of contents without a database; `am backup --health` fails when the last verification is older than `BACKUP_VERIFY_MAX_AGE_DAYS` (30 by default) or the scheduler heartbeat is stale. Restore drills are documented, and crypto-shredding makes erasure effective in backups. Restores replay erasures recorded after the snapshot, and `BACKUP_KEEP_DAYS` bounds how far back a restore point can be. Keep a rotated-out key in `MASTER_KEY_PREVIOUS` (or the old OpenBao/KMS version) for at least that window, because rotation does not rewrite old backups.
- Security headers, CSRF protection for cookie sessions, session revocation.
- Vulnerability disclosure policy (`SECURITY.md`) from the first public release.
- Target compliance frameworks for a future SaaS: SOC 2 / ISO 27001 — the audit log, RBAC, encryption and change management (artifact approvals) are designed to support them.

## 7. Multiple brands on one instance

A **brand is a workspace**. One installation can run several brands behind one login and one admin
host; people switch brand with the workspace switcher (`X-Workspace-Id`) and each brand may have its
own public link hostname ([identity.md](../identity.md#brands-and-domains-186)). The workspace is a
**brand and content boundary**, not a separate legal entity: the installation, encryption keys,
backups and billing are shared.

Everything a person or an agent reads or writes carries the workspace, so these are per brand:

- **Profiles.** Identity resolution is workspace-scoped. A person who subscribes to brand A and
  brand B has two profiles (`prf_…`), two event histories and two consent ledgers. Nothing merges
  across brands; the same e-mail address is two people, and `profiles.find` only searches the
  caller's brand.
- **Consent and topics.** Consent records, objections and topic choices belong to one brand. A
  `marketing_email` unsubscribe from A leaves B's consent untouched, and a preference-centre link
  (including a topic link) acts only on the brand named in its signed token and host.
- **Suppression.** Bounces, complaints and unsubscribes suppress within the brand that recorded
  them. A hard bounce on A does not suppress B. That is intended: each brand has its own sending
  identity and reputation. Sharing hard-bounce suppression across brands is a follow-up design, not
  current behaviour; the trade-off is tracked in
  [#430](https://github.com/TimChr78/Agentic-Marketing/issues/430).
- **Erasure and DSR.** `profiles.erase` deletes the person in one workspace: profile rows,
  identifiers, events, consent and topic history, and it destroys the per-profile key so copies in
  backups become unreadable. An erasure request that covers several brands must be **repeated per
  brand**; there is no cross-brand erase. The erasure log, tombstones and the suppression hash left
  behind are also per brand.
- **Exports.** `profiles.export` returns what one brand holds (profile, personal data, identifiers,
  consent, topics, events, AI decisions, ad uploads and push devices) and names that brand in
  `workspaceId`. An access or portability request covering several brands is one export per brand.
- **Sending.** Each brand has its own provider, From identity and sending domain, so reputation,
  deliverability, bounces and complaints are measured per brand. A brand without a verified primary
  domain falls back to `PUBLIC_LINKS_URL` ([email-and-sms-delivery.md](email-and-sms-delivery.md)).
- **Analytics and webhooks.** Metrics, campaigns, journeys, segments, outbound webhooks and their
  deliveries are workspace-scoped. There is no cross-brand report, and a query in A cannot see B's
  events; ClickHouse row policies enforce the same boundary as the command layer.
- **Agents.** An API token or OAuth/MCP connection belongs to exactly one brand; working in two
  brands needs two credentials. `X-Workspace-Id` switches a person's session, never a token or
  connection ([identity.md](../identity.md#one-brand-per-token-or-connection-187)).
- **Legal.** This is not a multi-entity tenancy model. Workspaces share the installation, encryption
  keys, backups and billing; the boundary separates brand content and audience data, not legal
  entities or data-protection regimes.

A DSR therefore starts from the person's profile in one brand: export and erase it there, then repeat
in every other brand that may hold the same person.
