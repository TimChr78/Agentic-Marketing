# Analytics & reporting

Decision: [ADR-0010](adr/0010-analytics-layers.md). Three layers; only the first is part of the core.

## Layer 1 — Built-in marketing analytics (core)

All events, message events, journey step logs and decision logs already land in ClickHouse ([data-platform.md](data-platform.md) §5), so marketing reporting is cheap to provide in-product:

| Report | Source tables | Notes |
|---|---|---|
| E-mail performance (sent, delivered, clicks, unsubscribes, complaints, bounces) | `message_events` | Open rate shown only where pixel tracking is enabled (off by default) |
| Journey funnel per step, waiting counts, drop-off | `journey_events` | Live overlay on the journey canvas |
| Goal conversion **with holdout uplift** | `journey_events` + `events` | Holdout/control groups per journey give incremental effect, not just attributed orders |
| Experiments (A/B/n) for messages and web experiences | `decision_events`, `events` | Frequentist, sequential and Bayesian (`experiences.results`) |
| Web personalization exposures & uplift | `decision_events` | |
| Segment growth, consent opt-in/objection rates | `segment_memberships`, consent ledger | Consent reporting doubles as GDPR evidence |
| Deliverability (per domain/provider) | `message_events` | |
| LLM usage & cost per journey/purpose | metering events | Feeds budgets |

Implementation:
- A small **metrics layer** in code: named measures and dimensions over curated ClickHouse views (`metric('email.click_rate').by('journey', 'day')`). Queries are parameterised and tenant-scoped; no raw SQL from the UI or from agents.
- Charts in the UI with **Apache ECharts** (Apache-2.0), themed from the design tokens.
- Every report is also a command (`analytics.*`) and therefore an **MCP tool**, so agents can evaluate their own changes ("did the v4 subject lines help?").
- Privacy: reports are aggregates; a minimum group size (e.g. k ≥ 5) can be enforced for breakdowns; the `analytics` purpose is respected at ingest.

### Implementation (Phase 16, #75)

The metric layer is its own workspace package, `packages/analytics`, rather than a folder inside `packages/events`. `events` owns ClickHouse transport and storage; campaign evaluation and alerts read metrics, so keeping the catalogue and query compiler separate lets those consumers depend on one package without importing the event sink. The package reads ClickHouse through the existing `EventStore` client (with `settingsFor(workspace)` so the row policy applies) and Postgres through the command transaction (workspace time zone, conversion map, segment members, published campaign members).

**Registry.** `packages/analytics/src/registry.ts` is the only place measure ids, descriptions, units, aggregations, sources, allowed dimensions and default grains live. `analytics.metrics.list` returns the same catalogue, so the UI picker and agents cannot drift from it.

| Source | Measures | Notes |
|---|---|---|
| `message_events` | `email.sent`, `email.delivered`, `email.bounced`, `email.complained`, `email.opened`, `email.clicked`, `email.unsubscribed`, `email.click_rate`, `email.bounce_rate`, `email.unsubscribe_rate`, `email.open_rate` | Each base measure counts distinct people (`profile_id`). Ratios are clickers/delivered, bounces/sent and unsubscribes/delivered. Opens exist only where tracking is enabled. |
| `journey_events` | `journey.entered`, `journey.completed`, `journey.exited`, `journey.goal_reached`, `journey.step_reached` | Distinct participants; `journey_step` is the node id, ordered by its first `seq`. |
| `events` | `conversions`, `revenue` | `conversions` counts distinct event ids named by the published `conversion_map` (or `filters.name`). `revenue` sums the map rule's `value` property; the currency comes from the rule or `currencyProperty`. |
| `segment_memberships` (Postgres) | `segment.members` | Current membership size; ignores `from`/`to`. |
| `campaign` | `campaign.recipients`, `campaign.converters`, `campaign.conversion_rate`, `campaign.revenue`, `campaign.revenue_per_recipient` | Joins message events for a published campaign's sending members to attributed conversion events. Conversions are first touch: people who converted within the goal's attribution window after their first campaign message, so a person reached by two campaigns can count for both. Revenue is per currency. Dimensions are the time grains and `campaign`. |

Dimensions are `day`, `week` and `month` (workspace time zone via ClickHouse `toStartOfDay`/`toStartOfWeek`/`toStartOfMonth`), `channel`, `template`, `broadcast`, `journey`, `journey_step`, `purpose`, `variant`, `message_type`, `segment` and `campaign`. Each measure declares its own list; an invalid combination is an `invalid_input` error naming the dimensions that would work. Message `variant` is stored on `message_events` (additive ClickHouse migration `0005`), so it can be reported without joining Postgres. `broadcast` and `journey` derive from the `bct_`/`jrn_` id prefixes; `message_type` is broadcast, journey, transactional or other. `campaign` is resolved from the published campaign's sending members: a message or journey event belongs to the published campaign that owns its broadcast or journey, and the filter takes campaign ids while ClickHouse receives their member ids. A `broadcast` order key sorts by first send, so "the last four issues" is one query with `dimensions:["broadcast"], order:{by:"broadcast",dir:"desc"}, limit:4`.

**Contract.** `analytics.query({measures, dimensions?, from, to, filters?, limit?, order?})` returns `{columns, rows, meta}`. Columns name a dimension or measure and unit; rows are arrays of `string|number|null`; `meta` carries the workspace time zone, the single currency (or null when several), the range, freshness (newest event in range), the suppressed row count, k and notes about opens, ratios and currency. Limits: 1–10 measures, 0–3 dimensions, at most 400 days, 1–5000 rows (default 1000). Filters accept one value or a list for template, broadcast, journey, channel, purpose, variant, conversion name, segment and campaign, subject to what the source supports.

The compiler (`packages/analytics/src/compile.ts`) builds every table, column, expression and alias from the registry, never from the request. Caller values travel only as ClickHouse `{name:Type}` parameters, and every time parameter is `DateTime64(3, 'UTC')`. Ratios are computed in the outer query from the aggregated numerator and denominator, so a rate is never an average of other rates; a zero denominator yields null. When revenue is requested the query groups by a `currency` column, so amounts in different currencies are separate rows and are never added together.

**k-anonymity.** When at least one requested dimension is not a time grain, any row whose base population (distinct profiles for message and journey events, distinct visitors for conversion events, membership count for segments) is below **k = 5** has all its measure values set to null and is counted in `meta.suppressed`. Time-series rows with only `day`/`week`/`month` are not suppressed. Every total the result exposes beside its rows is protected per total: the people total, each measure total and each per-currency revenue total. For each total, the rows are grouped by their independent population — the dimension key such as the campaign or member, never the physical currency row — and a contributor is hidden when its value for that total is suppressed, whether by the group size or by `revenueK` for revenue. When exactly one contributor to a total is hidden, the smallest visible contributor with a non-zero value in that total is hidden as well, for the same measure; hiding the people total's complement hides the whole row. Hiding a complement can make the same contributor hidden in another total, so the rule repeats until no total has exactly one hidden contributor. When a total has one hidden contributor and only zero-valued visible contributors, hiding a second would reveal nothing and the total is withheld (null) instead; that is the narrow option-A fallback, `meta.suppressed` still counts hidden rows and cells, and a note names every withheld total. Each total's tie goes to the first contributor in the result's deterministic order. A result with no non-time dimension has no total to protect and is not suppressed. The command description says rows below k are hidden and the result notes say when a complementary contributor or a withheld total was reported, so an agent can report suppression instead of guessing.

### What k = 5 promises

- Rows with fewer than **5** people behind them are hidden. When exactly one contributor to a total would be hidden, the smallest visible contributor with a value in that total is hidden too, separately for the people total, each measure and each per-currency revenue total. Totals stay visible, unless a total has one hidden contributor and no visible contributor with a value: then that total is withheld (null) and named in the notes.
- The named reports keep the same floor: a funnel headline total that is a positive count below k is withheld, a hidden branch hides its smallest visible sibling in the same fork (or merge) rather than an unrelated step, a headline that equals a hidden step is withheld with it, and a drop-off or rate from a withheld count is null. A campaign holdout's revenue is keyed on converters per currency, so a currency with fewer than 5 converters keeps its key with a null amount.
- It does not stop differencing across queries: comparing a breakdown with a different breakdown, a different time window or a different filter can still narrow a number down. Suppression is not differential privacy.
- Analytics access should be limited to roles that are allowed to see audience-level data. A principal who may not see a segment's size should not be able to query around the floor.

**Named reports.** `analytics.emailPerformance({from,to,by})` and `analytics.journeyFunnel({journeyId,from,to})` are thin wrappers over the same compiler and meta shape. The funnel adds per-step reached counts, drop-off and drop-off rate, plus entered, goal reached, completed and exited. Its headline totals come from the same rule: a positive total below k is withheld (null), and any drop-off or rate that would be computed from a withheld count is null. Suppression follows the published topology rather than a flat row list. A relation is a set of printed counts that add up: a fork's branches to their parent, a reconvergence's parents to the node, and every headline to the steps that produce its event (`entered` to the trigger steps, `goalReached` to the goal steps, `completed` to every terminal step — an exit node or a node with no outgoing edge). When exactly one term of a relation is hidden, the smallest visible term of that same relation is hidden as well (or the parent/node, or the headline total, when that is the only other term), repeated to a fixed point. A headline that cannot be expressed as a sum of printed steps — `exited`, which is recorded wherever consent is withdrawn or a wait ends, and any headline whose contributor has no row — is withheld whenever any step is hidden. Without a published version the relations are unknown, so every step row protects every total and the note says so. `meta.suppressed` counts withheld totals and complementary steps, and the note names them. `analytics.metrics.list` lists the catalogue with each measure's description, unit, aggregation, source, allowed dimensions and default grain, so a person or an agent can see what is available before querying. `analytics.campaignSummary({campaignId,from?,to?})` reports one campaign from the same layer: recipients, delivery, clicks, unsubscribes and complaints, converters, conversion rate, revenue per currency and per recipient, progress against the goal's target, the recipients → delivered → clicked → converted funnel, a row per sending member and the holdout result of journey members with a control group. A currency whose revenue the per-currency floor suppressed keeps its row with a null amount, so a revenue goal's target progress is withheld rather than computed from the visible currency. A campaign that has not sent returns a readiness state instead of zeros.

**Holdouts.** `journeys.holdoutResult` and `campaigns.holdoutResult` report, per arm (control and treatment), the people assigned, conversions, conversion rate and e-mail unsubscribes (the guardrail); the campaign result adds revenue per currency, keyed on the distinct people who converted in each currency. A currency whose converters in an arm are below k keeps its key with a null amount and is counted in `suppressedRevenue`, the same floor `analytics.query` applies with `k_revenue_group`; there is no arm revenue total or revenue per recipient to subtract it from. Both give absolute and relative lift, Newcombe's 95% interval for the difference of proportions, whether the minimum sample size is met in both arms, and a verdict. A verdict other than `not_enough_data` needs both samples and an interval that excludes zero. A journey inside a published campaign uses the campaign's control group, so the campaign is measured once across all its sending members; a journey outside one measures its own. Control groups add no measure to the registry: they reuse the `campaign` measures and the journey measures. Goal-event reads page the full attribution window by `(timestamp, event_id)` with no row cap and are scoped to the measured campaign's people, so a busy workspace cannot hide a late conversion (#366). `journeys.splitResult` (0.6.0) gives the same per-arm view for an A/B/n split node, and is what the lifecycle optimiser promotes or retires a variant on. Each entry counts at most one conversion and unsubscribe. A conversion with a recorded participant is attributed only to that participant's own split take at or before it: the participant id is the canonical identity across profile merges, so a later historical profile id does not move the outcome. A second entry that bypassed the split, converted before its own take, or has no take is not credited to another participant (#419). Only an outcome without a participant, such as an e-mail unsubscribe, uses the profile's latest entry at or before the outcome (equal timestamps break by participant id). A re-entrant who lands in another arm therefore cannot credit the same outcome to both arms (#369).

**Alerts.** `alerts.list`/`get`/`create`/`update`/`delete`/`test`/`history` evaluate deliverability (bounce or complaint rate above a threshold, with a minimum volume), signup drops and journey errors every five minutes through the metric layer. They notify once when a rule fires and once when it resolves, to a signed webhook or by e-mail to members. They reuse the compiler and meta shape rather than adding a second query contract. Configurable dashboards and a report builder are not built; agents read the metric layer, and the UI keeps fixed reports.

**Agent reports.** `agents.report` (0.6.0; counting fixes in 0.6.1) reports one agent for a period: actions by class and decision, undos and guardian episodes, the broadcasts it published and messages it sent, the journeys it published against their control groups, and its mandate goals measured on its own broadcasts. The agent page shows the last 30 days, and the hosted **Weekly report** template is a scheduled, read-only version of the same view. It is a report about an agent, not a configurable dashboard.

Campaign rows follow the same k-anonymity rule as the rest: the base population is the campaign's recipients, so a breakdown group with fewer than five recipients has its measures hidden and is counted in `meta.suppressed`. Campaign measures cannot share a query with the per-channel ones, because the compiler queries one source; `analytics.campaignSummary` runs them side by side and adds their suppressed counts. Its member rows are a breakdown under every campaign headline total: one member below k also hides the smallest visible member with a value, per total, so the member's numbers cannot be recovered from the recipients or another headline total. A total with one hidden member and only zero-valued visible members is withheld (null) and named in the notes (#692).

**Limits and operations.** Each ClickHouse query sets `max_execution_time = 10` seconds and `max_result_rows = limit`. Results are cached in memory for 60 seconds per workspace and normalised query. The server logs duration, returned rows and rows read (from ClickHouse's summary header when available). Segment sizes are read from Postgres, so they follow membership changes within the same 60-second cache.

**UI.** Insights → Analytics uses the catalogue for its measure and dimension pickers and runs the same `analytics.query` as an agent. A time dimension renders as an ECharts line chart through the existing lazy `Chart` component; the table shows the same numbers, suppression and notes.

## Layer 2 — Bring your own BI

- Documented, versioned **analytics views** in ClickHouse (`analytics.messages_daily`, `analytics.journey_steps`, …) with a read-only role and row policies per workspace.
- Works with Metabase, Apache Superset, Grafana, Power BI, Tableau, Looker Studio (ClickHouse connectors exist for all of them).
- Warehouse export ships: a scheduled export to Postgres or S3-compatible storage as gzipped NDJSON (`warehouse.create`, `warehouse.run`; see [data-platform.md](data-platform.md) §7 and [integrations.md](../integrations.md#warehouse-export)).
- Not embedded in the core: Superset is a heavy Python stack, Metabase is AGPL with paid interactive embedding, Grafana is AGPL. All three remain excellent external tools.

## Layer 3 — Forward to dedicated analytics tools

General web/product analytics is not rebuilt. Events can be forwarded as **destinations**:

| Tool | Fit | Integration |
|---|---|---|
| **Umami** (MIT, self-hosted — the owner already runs it for martechsignal.com) | Privacy-friendly web analytics, cookieless | Destination that forwards page views and selected custom events to Umami's `/api/send` endpoint with the site's website id; consent-aware |
| Matomo (GPL, EU-friendly) | Full web analytics, GDPR features | HTTP Tracking API destination |
| PostHog (MIT core) | Product analytics, funnels, session replay | Capture API destination |
| GA4 | Ubiquitous, but US transfer concerns | Measurement Protocol destination, off by default |

Because ingestion is Segment-spec compatible, the reverse also works: a site can keep its existing Umami script and add our SDK, or send everything through our SDK and let us fan out.

## Upgrade path

If the metrics layer grows into a full semantic layer, **Cube** (Apache-2.0) can sit on top of ClickHouse and serve both our UI and external BI with one set of metric definitions.
