## Verified: baseline bugs are actually fixed

**#368 (truthful webhook ledger).** Baseline `notifyWebhook` inserted `deliveries.status = 'pending'`

**#370.** Baseline set `status: 'failed'` on the first chunk throw

queued/running and the committed cursor/counts/pins are untouched because the chunk and its cursor

**#375.** Baseline held `withWorkspace` across `tokenRequest`

## Findings

### F1 — #368 retries stop at the episode boundary; `retryable: true` is persisted with no retrier (P2, new scope gap)

`packages/alerts/src/evaluate.ts:286-301` and `:305` are the only places a rule's channels are
selected: a resolved episode (`!open` → return) and a disabled rule (not selected) never reach
`notifyFor`. `reconcileQueuedAlertEvents` deliberately never enqueues (`evaluate.ts:311-344`), so:

- a **resolved** notification whose webhook dies after the outbox's ~17 h budget (one cycle only —
  there is no second tick for that event) is permanently lost;
- a **firing** delivery that turns `dead` *after* the episode resolved (or the rule was disabled) is
  never re-opened either.

Meanwhile `reconcileAlertNotifications` writes `retryable: true` for both
(`notify.ts:249,255`), because the bound is `cycles < 2` — the same flag `pendingChannels` uses to
mean "will be retried". Repro (no clock tricks): rule fires, endpoint 500s; episode resolves 30 min
later; wait ~17 h; the resolved ledger entry becomes `failed, retryable: true`, and no path ever
re-selects it. A disabled rule mid-backoff behaves the same.

Minimal fix (either):
1. In `reconcileQueuedAlertEvents`, also select events whose webhook ledger has
   `status = 'failed' && retryable != false`, and re-open that delivery row (status `pending`,
   `attempts = 0`, `next_attempt_at = now()`, record `cycles + 1`) — the payload is already on the
   row, so no evaluator context is needed; or
2. keep reconciliation-only but set `retryable: false` for entries belonging to a resolved event or
   a disabled rule, so the ledger never promises a retry that cannot happen.

Note this is beyond the audit's literal test ("the next evaluate tick re-enqueues") but matches the
review scope's "retries including resolved episodes/disabled rules".

### F2 — the UI repeats #368's lie for `queued` (P2, pre-existing code path now wrong)

`apps/web/src/pages/insights/AlertsPage.tsx:179-185` counts only `status === 'failed'` as "not sent",
so after `alerts.test` returns a `queued` webhook plus a `sent` e-mail the toast says
"Test notification sent to 2 channels". The API is now truthful; the presentation is not.
Fix: treat `queued` distinctly ("e-mail sent; webhook queued for the outbox"). Not a PR regression —
the baseline never returned `queued` — but it is the user-visible half of #368 and was missed because
no web file was touched.

### F3 — dead→re-open is check-then-act; a `done` row can be resurrected (P3, new, low likelihood)

`packages/alerts/src/notify.ts:195-216`: `current` is read without a lock, then the row is reset with
`WHERE workspace_id = ? AND id = ?` only (`:212`). Interleaving with two evaluator replicas (supported):
A reads `dead`; A updates to `pending` and commits; the delivery worker sends and writes `done`; B,
which read `dead` before A's commit and had not yet reached its `UPDATE`, resets the row to `pending`
with `attempts = 0` → the worker sends the same alert again. The window is the microsecond span
between B's `SELECT` and `UPDATE`, so this is hard to hit, but the guard is one predicate:

```ts
.where(and(eq(...workspaceId), eq(...id), inArray(schema.deliveries.status, ['dead', 'failed'])))
```

and on no returned row, re-read the row and return its real state (instead of the stale `pending`).
This also makes `if (!reopened)` meaningful.

### F4 — the retry budget is not self-contained; a missing ledger entry re-arms it forever (P3, new, robustness)

`notify.ts:196-198`: with `existing === undefined`, `cycles` becomes 1 but `previous` is `undefined`,
so `notificationOf` omits `cycles` (`:128`) and the persisted entry carries no budget. Every
subsequent death then computes `cycles = 0 + 1` again → unbounded re-opening of a dead endpoint, which
is exactly what `MAX_ALERT_DELIVERY_CYCLES` exists to prevent. Normal flows keep the ledger entry
(`mergeNotifications` never drops entries), so this needs a rewritten/lost ledger or a future caller
that enqueues without a ledger — but the invariant is currently "the budget survives only in
`alert_events.notified`". Minimal fix: persist a `redeliveries`/`cycles` counter on the delivery row
(or derive the cycle from `attempts` history plus a row marker) and bound on that, using the ledger
only as a mirror.

### F5 — the #370 server test does not exercise what it claims (P3, test strength)

`apps/server/test/bulk-enroll.test.ts:236-300` wraps `withWorkspace` and rejects **before**
`processChunk` runs (`:255-262`), so no partial chunk is ever rolled back. It does guard the baseline
(baseline would set `failed`, so `status: 'running'` / `attempts: 1` fail) and it does guard
cursor/count preservation. But:
- the duplicate assertion (`:280-291`) cannot fail for a cursor regression: inserts carry
  `entryKey = bulk:{jobId}:{profileId}` (`enrollment.ts:376`) and the partial unique index
  `journey_participants_active_entry_key` (`migrations/0039...sql:9-10`) covers `ready|waiting`
  participants, which is the state of everyone in this fixture (30-day wait). A re-scan of an
  already-enrolled boundary is silently `skip('duplicate')`, not a duplicate row.
- a mid-chunk failure (the real atomicity claim) is untested.

Suggested stronger version: fail the Nth statement inside the chunk (e.g. a tx-wrapper that throws
after `journeyParticipants` inserts, or `SET LOCAL statement_timeout`), then assert the participant
count for that boundary profile is unchanged and `cursor/entered/skipped` equal the previous chunk's.
The `runUntilSettled` helper (`:58-66`) has no clock advance, so any test that leaves a real 10 s
backoff would spin out after 12 runs and return a still-running job — only the zero-backoff override
hides this (`bulk-enroll.test.ts:262-268`).

### F6 — release-surface ownership (P4, process)

`packages/db/src/migrate.ts:102` adds `'0073_ops_reliability.sql': '0.7.4'` while every version surface
is 0.7.3. `apps/server/test/version.test.ts:75-83` only requires truthiness, so CI passes, but
`lastServerVersion()` on a freshly migrated DB (no `server_versions` row yet) now reports **0.7.4**
(`migrate.ts:117-130`), and the 0.7.4 plan reserves the migration mapping/release surfaces for the
parent ("Parent updates release surfaces and migration mapping together after selecting the final
cut"). Keep it to keep CI green, but the parent must re-cut it if the final release is not 0.7.4, and
if the audience workstream lands `0072` first the head mapping must still be re-decided at merge order.
`CHANGELOG.md` is untouched, consistent with the same rule.

## Checked and sound (no action)

- **Migration 0073** applies: `CREATE INDEX`/`ALTER TABLE` verified by a fresh `migrate()` in the
  disposable DBs I ran; head/columns/indexes match `schema.ts` (`attempts`, `next_attempt_at`,
  `oauth_refresh_lease_until/token`, `alert_events_notified`). Adding NOT NULL columns with a constant
  default is metadata-only on PG11+.
- **Privileges/RLS:** `am_app` already has `UPDATE` on `deliveries` (`migrations/0009_integrations.sql:89`),
  `SELECT, INSERT, UPDATE` on `alert_events` (`0043_alerts.sql:56`), and table-level grants on
  `connections`/`enrollment_jobs` cover the new columns. The re-open `UPDATE` and the evaluator's
  `UPDATE alert_events` run under `app.workspace_id`, and `FORCE ROW LEVEL SECURITY` is in place.
  The sweep's admin workspace enumeration matches the existing `evaluateAlerts` pattern (admin is the
  documented RLS-bypassing owner role). Defense-in-depth only: the per-workspace sweep query and
  update omit an explicit `workspace_id = $1` (`evaluate.ts:324-333`), so they are safe *because* of
  RLS; adding the predicate would also help the planner.
- **`#376` lease lifetime vs HTTP:** `safeRequest` defaults to a 10 s deadline (`egress.ts:179-193`)
  against a 120 s lease, so a normal refresh cannot outlive its lease. A >2-minute stall between
  claim and write-back is the only way to reach the residual interleaving where a re-claiming
  replica's `invalid_grant` marks `error` just before the first replica's valid tokens are written
  back (write-back then returns early on `oauthStatus !== 'connected'`, `oauth.ts:381`). Residual,
  not reachable with the shipped timeout; a mitigation would be to allow persisting fresh tokens over
  an `error` state when the lease token still matches.
- **`#370` interleavings:** a stale failure-recording transaction cannot corrupt a concurrent
  successful chunk — it takes the job row `FOR UPDATE` (`enrollment.ts:469`) and only writes
  status/attempts/next/error, never cursor/counts/pins. `SKIP LOCKED` prevents two chunk runners.
- **No MCP catalog drift:** `scripts/gen-mcp-tools.ts` renders name/effect/permission/description
  only; no changed command description, so `.claude/skills/.../tools.md` stays valid
  (`apps/server/test/mcp-tools-doc.test.ts`).
- **Test infra:** `packages/db/test/disposable.ts` creates unique `am_<prefix>_<pid>_<hex>` databases
  and drops them; it never touches `am_test_template`. Two caveats, not blockers: (a) it connects
  `appUrl` with the admin/superuser URL, so these tests would not catch a missing `am_app` grant or an
  RLS policy gap (I verified the grants manually, above); (b) it `ALTER ROLE ... PASSWORD` on a
  cluster-global role, so two concurrent package-test processes share one test role.

## Preexisting limits (not introduced here, noted for the release notes)

- `runTokenRefresher` selects `< now + 10 min LIMIT 100` with no `ORDER BY` and refreshes
  sequentially (`oauth.ts:424-428`); a mass expiry or a slow provider can delay connections beyond
  the window (baseline identical). The lease improves safety, not throughput.
- `deliverDue` also enumerates `DISTINCT workspace_id ... LIMIT 100` unordered
  (`packages/integrations/src/deliveries.ts:182-185`), same starvation shape as the new sweep.
- Pre-upgrade ledger rows say `sent` while the delivery was only queued; the new sweep looks only for
  `queued` (`evaluate.ts:316-318`), so those rows stay falsely `sent` for already-resolved/disabled
  episodes. Firing episodes self-heal on the next evaluation.
- A scheduled refresh that wins during a re-authorization clears `oauth_pending` in `storeTokens`
  (`oauth.ts:108`), so the person's fresh `/oauth/callback` link is rejected. Baseline behaviour;
  the lease does not change it.
- Re-enabling a webhook endpoint does not un-exhaust an already-failed notification (firing or
  resolved); the alert is still lost, now truthfully.
- `CREATE INDEX alert_events_notified` is not `CONCURRENTLY`, so the startup migration takes an
  ACCESS EXCLUSIVE lock on a large `alert_events` table. Consistent with the repo's migration style,
  worth a mention in the upgrade notes.
