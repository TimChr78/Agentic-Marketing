## 1. P1-C — merge-survivor restore

`audiences.ts:1037-1055` now reads the survivor's intent in the same transaction (`:1038-1052`) and
builds the restore with the normal planner:

```ts
const restore = planMemberWrite({ profileId: survivor, current, stored: survivorRow.hashes, intent: intent?.hashes ?? null });
restores.push(restore ?? { profileId: survivor, remove: [], add: current, final: current });
```

- **Stored provenance is used.** `planMemberWrite` (`:131-152`) emits `obsoleteHashes(stored, current)`
  as `remove` (`:144-145`), so stale / disjoint identifiers are sent as provider removals in the same plan.
- **Intent is used.** `intent && !sameHashes(intent, current)` is added to `remove` (`:146`), so an
  ambiguous already-uploaded set is removed (or blocks the whole plan) rather than acknowledged.
- **Fallback is genuinely null-only.** With `current` non-null, `stored` non-null, `intent` null,
  `planMemberWrite` returns `null` only when `remove` is empty and `addedHashes` is empty, i.e.
  `stored == current` (`:149-151`). That is the case where a re-add is still needed after the
  merged-away member's removal; it cannot cover an obligation, and there is no intent to delete.
- **Ordering.** `writePlans` runs `ownedElsewhere` → partial gate (`:763-771`) → `remove` → only then
  `recordAddIntents` + `add` → `finalizePlans` (`:775-831`). Every failure path sets
  `retryableError`/records the error and skips finalize, so the old hashes and the intent stay.
- **Finalize is scoped to covered profiles.** `finalizePlans` deletes intents only for the profiles in
  `safe` (`:707-718`); a partially shared restore never reaches it. `finalizePlans` is also called with
  an empty `safe` for partial-only batches (already possible on the non-`stopOnError` paths); `chunks`
  returns `[]`, so this is a no-op transaction.
- **Interleaving with `processCurrentIntents`** (which runs first at `:1667`): if it resolves the
  survivor's intent, the intent is gone and the restore sees `stored` already updated (or computes from
  the new row) — correct. If it is blocked as partial, the intent survives and the restore re-includes
  it and is blocked again — correct. `syncAudience` holds the per-target session advisory lock across
  the whole platform run (`:1843-1857`), so the gap between the merge transaction's intent read and the
  restore's `writePlans` cannot be filled by another sync of the same target.
- **Partial-survivor case.** If the survivor's own row was orphaned by an earlier partial write, the
  restore's `remove` contains the same obsolete set, is re-classified partial, is excluded from `safe`,
  re-marks the row + intents (`coalesce(orphaned_at, now())` keeps the original timestamp) and never
  finalizes. The `stored == current` fallback can only clear markers whose obligation was exactly "the
  connection was unavailable / settings unusable" — the same re-add that `processReconcile:1173-1179`
  already performs for a re-enabled connection, and merge repair cannot run while `current` is
  unresolved (`fullPlatform:1656-1666`). Not a silent clear.

**Regression check of the new `stale` mode** (test `:724-789`): the survivor's ledger row is replaced
with `{historical-stale, historical-phone-stale}` and the fake remote member is mutated to match. The
merge repair then removes the merged-away member, the restore removes the stale set and adds the current
one, leaving exactly one current member; a subsequent erasure empties the audience. On the pre-fix code
`remove` was empty, the historical member survived, `membersOf` would be 2 after the merge and 1 after
the erasure — both assertions fail. Genuine regression, and it exercises the stored-hash leg.

**Regression check of the new `intent` mode** (`:724-789`): an orphaned intent with a different set is
seeded, and another sync's row at the same destination owns only its e-mail, so the intent set is
partially shared. The restore plan now includes that intent, the partial gate excludes it, and the test
asserts the intent row still exists with its original hashes and a truthy `orphaned_at`; on the pre-fix
code `finalizePlans` deleted it. Genuine regression for the marker/intent leg.

## 2. P2-A — bounded reconcile progress past manual obligations

- `writePlans` no longer returns early on a partial plan with `stopOnError` (old `:769` removed); the
  plan is simply not in `safe`, so its remove is never sent, `finalizePlans` runs only with `safe`, and
  the batch continues. `retryableError` is set only for no-connection/`callFor`, provider remove/add
  failure and ledger-write failure (`:747,753,816,823`).
- `processReconcile` now computes `next` from that flag (`:1192`): a manual obligation gives
  `complete ? null : lastId` (the last scanned profile id of the page, `:1189`), so the cursor moves past
  the obligation; a transient or DB failure gives `outcome.lastOk ?? cursor`, which is the last
  *finalized* safe profile (never a partial one, `:831`) — a conservative re-run from the last committed
  batch boundary. `lastOk` is only advanced after a fully successful batch, so a failure never skips an
  uncommitted plan.
- Visibility is preserved, not traded away: the partial path still marks the row + intent orphaned and
  pushes the manual reason (`:768-771`), so `countsFor` reports `unresolved > 0` and
  `ads.audienceBacklog` lists the member/intent; `listAudiences` shows `status: error` while
  `unresolved > 0` even when the last state row says `ok`.
- `complete` is computed from scanned rows, not plans (`:1189`), so a page that is entirely partial
  still advances or wraps; nothing earlier in the page is skipped because the cursor is `lastId`.
- **Regression test** (`:790-820`): `maxReconcilePerRun: 1`, two runs. Run 1 selects the blocked profile
  (asserted to sort first), records the partial obligation and advances to it; run 2 reaches the later
  profile and uploads it, while the backlog stays at one entry. With the old `errors.length` branch the
  cursor would stay at `null` and run 2 would re-select the blocked profile — the `progress-b` assertion
  fails. Genuine regression for the starvation case.

## 3. P2-B — ownership exclusion at the same remote target across destination keys

Both halves of `ownedElsewhere` now exclude only the plan's own key:
`AND NOT (sync_id = syncId AND destination_key = <ref key> AND profile_id = ANY(ids))` (`:617`, `:627`),
while the row match still requires `destination_id` (and, outside Meta, the same operating/login account).
Consequences checked:

- **Evacuation retry to the same Meta target.** Run 1: old-key removal applies then fails (the fake
  applies before the 500); the old row is orphaned and kept, and `processAdditions` creates the new-key
  row and remote member. Run 2: the old-key plan's remove values are now owned by the same sync's
  *new-key* row at the same `destination_id`; the set is fully shared, so `send.remove` filters it out
  (`:775`), no provider removal is sent, and `finalizePlans` closes the covered old row. The person
  stays. Without the `destination_key` term the same-sync exclusion hid the new-key row and the retry
  deleted the live member while the new-key ledger row remained — the test's "1 member after run 2"
  assertion catches exactly that.
- **Partially overlapping new-key row** ⇒ the old plan is classified partial and preserved as a manual
  obligation; the live member is never deleted. Correct.
- **No leak across genuinely different destinations.** The query still pins `destination_id` (and the
  Google account), so rows at a different audience/list were never in scope. Two destination keys with
  the same `destination_id` denote the same remote member reached through different connection
  provenance; skipping the removal and dropping the old row is therefore covered by the current key's
  row, and when the current key has no row for the profile the old row is removed normally.
- **Ordering.** Prior destinations are evacuated before the current destination (`:1615-1655`), so a
  current-key row is present when the old key is retried; leaver removal then sees no stale old row for
  the same target (each run's evacuation either closes or preserves it).

**Regression test** (`:822-836`) is the interleaving above and asserts status error then ok with one
member throughout. It fails on the pre-fix predicate (0 members after the retry).

## 4. Remaining findings

### P2-1 (pre-existing, same silent-loss class; not caused by this correction) — merge repair still deletes an uncovered intent of the *merged-away* row

`processMergeRepair` builds the merged-away removal with `intent: null` in both branches
(`:992` for a dangling chain, `:1024` for an existing survivor with different hashes). `finalizePlans`
then deletes **every** intent for the plan's profile id at that key (`:707-718`), whether or not the
plan's `remove` covered its hashes. `processCurrentIntents` runs first, but it leaves an intent behind
when its plan is partially shared, or when the intent page limit (`MAX_INTENTS_PER_RUN = 10_000`,
`:38`) is exhausted before this profile; merge repair can then consume it in the same run.

Reproducible interleaving (single Meta sync at audience X, no real merge needed — a tombstone suffices):

1. Merged-away profile M has a ledger row with hashes `S = {m1, m2}` and a durable add intent
   `I = {m3, m4}` (the add was applied but the response/ledger write failed). Another sync's row at the
   same destination owns `m3` only, so `I` is partially shared (`1 of 2`).
2. Run 1, `processCurrentIntents`: M resolves away from its own id, so `current = null` and the plan is
   `remove: [S, I], final: null`. The partial gate on `I` excludes the plan and marks M's row + intent
   orphaned; nothing is sent.
3. Same run, `processMergeRepair`: M's row still exists, survivor V has a row whose hashes differ from
   `S`. The M plan is built with `intent: null`, so its only remove set is `S`. If `S` is unowned (or
   fully owned), the plan is safe: the provider removes `S`, and `finalizePlans` deletes M's row **and
   `I`**.
4. `{m3, m4}` may still exist at the provider with no row, no intent, no orphaning and no backlog. Next
   run is `ok`; erasing V/M never removes `m4`, because no ledger or intent holds it. This is exactly
   the P1-C/P1-B failure shape, on the other profile of the merge.

This path predates the delta (identical at `2a27f0a` and `b809cba`) and is not touched by
`ccf8d87..HEAD`, so it does not affect the verdict on the correction.

**Minimal fix (mirror of the survivor fix):** read the merged-away row's intent in the same transaction
and pass it to the planner in both branches, e.g. apply the same pattern as `:1038-1053` with
`profileId: row.profile_id` and `stored: row.hashes`, then push `plan` only if non-null. The intent's
hashes then enter `remove`, so the partial gate preserves the row + intent (and an unowned intent is
removed before finalize). Regression: seed M's row + a partially-shared orphaned intent at the key,
tombstone it into V with differing hashes, run with `maxReconcilePerRun: 0`/`maxAddsPerRun: 0`, and
assert the intent survives orphaned and the backlog remains 1 (and, if the `S` removal is made to
execute, that `I`'s map is still referenced by the ledger).

### P3 / observations (no action required for this correction)

- The merged-away/ survivor `intent` selects have no `op` filter, `ORDER BY` or `LIMIT` (`:1038`, `:996`
  style). Harmless today: migration `0072` constrains `op IN ('add')` and the unique key allows exactly
  one row per profile, so the destructure is deterministic.
- The restore fallback (`:1055`) clears an orphan marker when `stored == current`. That is the same
  behavior as `processReconcile:1172-1177` (re-add after the connection is reachable again) and cannot
  clear a partial-ownership marker; a comment on the fallback could make that explicit.
- In the `sameHashes(survivorRow.hashes, row.hashes)` branch (`:1008-1023`) the duplicate row is deleted
  without an immediate restore. If the survivor's stored set is itself stale, reconciliation (or the
  cursor wrap) fixes it; no ownership/provenance is overwritten, so this is only an incompleteness of
  "immediate" repair, not a loss.
- Stale comments flagged by the first delta review are unchanged: `ownedElsewhere`'s docstring still says
  ownership is checked "by profile id" (`:591-594`), it still returns an unused `profiles` set, and the
  `audienceMembers.destinationKey` comment in `schema.ts:529-537` still lists the Meta ad account as part
  of the identity. They invite the removed behavior back; docs-only.
- `countsFor` still counts an orphaned intent in both `orphaned` and `pending` (`:1353-1364`), so
  `unresolved` can be 2 per obligation (pre-existing, over-reporting only).
- `processMergeRepair`'s returned `repaired` counts only the merged-away removals, not the restore's
  removals (`:1091`); metrics only.

## 5. Test-coverage assessment (static; server project not executed here)

The four new cases are in the server project, so I read them and their fake harness rather than running
them (the parent's expanded gate is pending). They are honest regressions:

- The fake models membership (remove deletes any member matching any payload hash), so the stale case
  cannot pass by request-count coincidence; the `stale` mode additionally erases the survivor and
  asserts the audience is empty, which is the end-to-end guarantee that was at stake.
- The `intent` mode seeds the competing owner at the *same* `destination_key` but a different `sync_id`,
  so the ownership query includes it without needing a second real connection; it asserts the intent's
  exact hashes and `orphaned_at`, not just the status string.
- The cursor test uses `maxReconcilePerRun: 1` and an explicit `blocked < later` guard, so it really
  proves the cursor moved past the obligation rather than that both fit a page; it also asserts the
  backlog remains (the obligation is not silently dropped).
- The same-target test applies the removal before the injected 500 (`failRemoveAfterApply`), which is
  what makes the retry dangerous; it asserts one member after both runs and status error → ok.
- The static SQL tombstones (`UPDATE profiles SET merged_into = …`) are an explicit stand-in for the
  post-merge seam; the real resolver merge is covered by the earlier merge test in the same file, and the
  comment says so. Acceptable, and it avoids making the coverage test depend on resolver timing.
- Not covered (and not required by the correction): the merged-away partial-intent loss in P2-1; a merge
  into a survivor whose *member-level* obligation is partial (the `intent` mode covers the analogous
  intent case); the `sameHashes` stale-survivor sub-case.

The pure-helper suite still passes 16/16. No shared-database test or migration was run by me.

## Bottom line

The correction does what the resolution says: the immediate merge restore is planned from the survivor's
stored hashes **and** its durable intent, the unconditional add is only the "nothing to change" fallback,
all provider removals precede finalization, a partial survivor obligation stays orphaned and visible,
the reconcile cursor now advances past manual obligations while transient provider/DB failures still pin
the retry cursor, and ownership exclusion only ignores the plan's own destination key so a new-key member
at the same Meta audience survives an evacuation retry. The new tests would fail without each fix.

No remaining P1 in the reviewed delta. One pre-existing P2 (merged-away intent can still be deleted by
`finalizePlans` without removal coverage) sits in the same transaction and is worth a small follow-up;
it is not introduced by, and does not weaken, the correction under review.
