## Corrections made during integration review

- The warehouse change-marker migration uses separate INSERT and UPDATE triggers; an earlier draft incorrectly referenced trigger variables in an SQL WHEN expression.
- Private erasure keys use a single bound Postgres array parameter rather than an expanded SQL tuple. Events-only erasure is tested against the actual destination database.
- Incomplete erasures retain the erasure cursor and remain failed on repeated runs. No deletion keys are captured without a warehouse destination; deleting the final destination removes leftover keys.
- The direct-export safety fixture controls the warehouse scheduler to avoid concurrent DDL. The warehouse loop's idle delay is abortable, so shutdown does not wait for the whole polling interval.
- Old signed topic/preference links resolve the surviving identity; topic writes serialize with identity merges and re-resolve in their transaction.
- An edge target lookup failure aborts erasure instead of silently skipping deletion. A previous-target cleanup failure remains visible in `lastError` while a new target successfully syncs.
- Fixture corrections use a non-PII role that actually holds `profiles:read`, normalize raw SQL timestamps, and isolate snapshot membership criteria. Events-only exports include identify events too; the assertion pins the intended track event and verifies all of the person's events disappear.

## Publication gates and limits

An independent read-only review of warehouse/edge lifecycle and concurrency is pending. The PR remains draft until blockers are resolved. Full GitHub CI (server suite, e2e, Docker smoke, Helm, static checks and dependency review) must pass before merge; the release workflow repeats its CI gates before publishing.

Legacy warehouse erasures may lack deletion keys and require manual downstream cleanup; they are reported as incomplete rather than successful. New destination configurations should point to a clean destination, not be used to conceal unresolved data in an old one. Cross-account edge cleanup needs a token that can access the old namespace or manual cleanup; outstanding targets remain visible. KV propagation and worker cache expiry bound revocation, as documented in the edge deployment guide.
