## 3. Per-issue findings

### #347 — P0 — Unbounded JSON bodies on password reset and copilot
**Confirmed.** `body()` (`apps/server/src/http/password-reset.ts:103-106`) calls `c.req.json()` with no size gate; `requested()` calls it at line 120 **before** the first rate-limit check at line 125, and `resetPassword()` at line 150 before the token check. `passwordResetRoutes` is mounted at `apps/server/src/app.ts:231-239` with no `bodyLimit`; the only limits in the server are MCP (`app.ts:320-331`) and REST (`http/rest.ts:83,97`). `copilot.ts:126` does `await c.req.json()` before `Body.safeParse`, after session auth.
**Impact:** three unauthenticated, unrate-limited public POSTs that buffer an arbitrary body before any work; `newPassword` is then forwarded to Better Auth for hashing. Chunked encoding defeats any absent `Content-Length` assumption. No default proxy limit exists in `deploy/helm` (`ingress.annotations` is empty in `values.yaml:81`, operator-supplied), so a default deployment is exposed.
**Regression test:** add cases to `apps/server/test/body-limits.test.ts` (today it has no reset/copilot case) asserting 413 for a body over the limit on `/api/auth/forgot-password`, `/api/auth/forget-password`, `/api/auth/request-password-reset`, `/api/auth/reset-password` and `/api/copilot`, and asserting a legitimate ~1 KiB request still works.

### #348 — P1 — Agent can delete human-authored memory notes
**Confirmed.** `deleteHostedMemory` (`packages/auth/src/hostedAgents.ts:634-654`) resolves the row, calls `assertMemoryScope` (`:491-495`) and deletes. `assertMemoryScope` compares only `ctx.principal.agent.id !== agentId`. `createdByRunId`/`createdByUserId` are written on add (`:579-596`) and exposed as `createdBy` (`:476`) but never consulted on delete. Docs contradict the behaviour: `docs/agents.md:102` ("people any, the agent its own") and `:106` ("the agent may delete its own notes").
**Impact:** an autonomous run can erase constraint/context notes a person wrote for its next runs, with no trace except the ledger. No cross-agent or cross-tenant escape (scope check still holds).
**Regression test:** in `apps/server/test/hosted-memory.test.ts` (next to the person-delete case at :215) add: person writes a note → agent principal calls `agents.memory.delete` → expect `forbidden`/`conflict`; agent-written note → delete succeeds; person deletes person note → succeeds.

### #349 — P2 — Memory caps race
**Confirmed.** `memoryUsage` (`:505-515`) is a `count(*)`/`sum(char_length)`; `addHostedMemory` reads it (`:568`) then inserts (`:588-598`); `updateHostedMemory` reads it (`:619`) then updates (`:626-630`). Migration `0065_hosted_memory.sql` has only a PK and a lookup index — no check constraint, trigger, or per-agent serialisation.
**Impact:** documented hard caps (50 notes / 10,000 chars) are advisory under concurrent MCP/API writers. `loadRunContext`'s prompt-side cap (50 notes / 3,000 chars) hides the drift from the model while `agents.memory.list` reports `count` above `limits`.
**Regression test:** same file, two concurrent `agents.memory.add` from 49 notes and from 9,500 chars, plus an add/update race; assert the final `count`/`characters` never exceed the limits and the loser gets `conflict`.
**Fix note:** the read and insert already share `ctx.tx`, so a `pg_advisory_xact_lock(hashtext('hosted-memory:' || agentId))` before `memoryUsage` is sufficient and matches the `reserveTokens` pattern; a DB trigger is the belt-and-braces option.

### #350 — P1 — Routed probability ≠ stored probability for choice questions
**Confirmed, reproduced.** `steps.ts:398-400` computes `probability = first.probabilities[answer]` for routing, while `parseSystemOneAnswers` (`decision.ts:156-168`) sets the answer's own `probability` to `probabilities[chosenLabel]`; `storeProfileScore` writes `answer.probability` (`decision.ts:330,341`) and `ai.score` returns/stores the same (`score.ts:165`). Repro: criteria `{email,sms}`, `answer:'email'`, provider chose `sms` with `{email:0.2, sms:0.7}` → route 0.2, store 0.7.
**Impact:** segment conditions (`segments/src/evaluate.ts:250-263`) and later decision steps read a probability the journey never routed on — a person can be routed on one side of a threshold and targeted on the other. Silent; only choice questions with explicit `answer` are affected (the existing test at `apps/server/test/decision-models.test.ts:252` uses a noul question).
**Regression test:** end-to-end choice node in `apps/server/test/decision-models.test.ts` with the model choosing a label other than `answer`; assert routed edge **and** `profiles.scores.value` both equal `probabilities['email']`.

### #351 — P2 — Participant woken before the score is stored
**Confirmed.** `finish(...)` at `steps.ts:401-415` commits `due_at = now()` on `journey_participants` (`:130-137`) in its own transaction; `storeProfileScore` runs afterwards at `:416-425` in a separate transaction with `.catch(logger.error)`. A worker can claim the participant in between.
**Impact:** a following branch/segment step can read a missing or previous score; a failed score write is invisible to the journey and only logged. Reachable under normal scheduler timing, not only a failure.
**Regression test:** in `apps/server/test/decision-models.test.ts`, make `storeProfileScore` fail/pause (inject a throwing service or a poisoned `scoreKey`) and assert the participant does **not** advance, or that a branch immediately after the decision sees the new value.
**Interaction:** fix together with #358 (both edit the `finish` call contract) and #350 (both change what `storeProfileScore` receives).

### #352 — P1 — Privacy guard is bypassable
**Confirmed, reproduced.** (a) `personalDataIn` returns `null` for any object at `depth > 8` (`packages/ai/src/context.ts:76`), so a 9-level nested `{email: …}` passes. (b) `assertStateAllowed` (`decision.ts:222-230`) is the only sweep and is applied to `state` only (`score.ts:127`, `steps.ts:380` via `nonPersonalState`); `systemOneRequest` sends `state` **and** the wire questions (`decision.ts:120-125`), and both `logCall` (`score.ts:211`) and `finish` (`steps.ts:147`) persist `input.questions`.
**Impact:** with `allowPersonalData: false` (the default; `docs/decision-models.md:40-47` says JEV/CommandCode has no ZDR path), an e-mail in `instructions`/`criteria` is sent upstream and stored in clear in `ai_calls`, while the audit trail looks clean. The nested-state bypass is accidental and reproducible.
**Regression test:** `packages/ai/test/decision.test.ts` — depth-9 nested `{email}` must throw `personal_data`; a question `{instructions: 'Write to ada@example.com'}` must be refused for a non-ZDR provider (and, if logging is kept, redacted). Also assert `assertStateAllowed(state, questions, provider)` or the equivalent new signature covers both.

### #353 — P2 — Out-of-range probabilities/confidence/token counts accepted
**Confirmed, reproduced.** `number()` (`decision.ts:127-130`) only checks finite; `distribution()` (`:132-138`) accepts any finite number per key; the choice branch (`:161-168`) applies no 0–1 check to `probability` or `confidence`; `callSystemOne` (`:280-281`) accepts any numeric `usage.*` and `recordAiCall`/`usedThisMonth` (`providers.ts:45-67`) sum it. Repro returned `probability:-0.7, confidence:5, probabilities:{email:1.7, sms:-0.7}`.
**Impact:** a buggy/compromised provider makes every threshold pass, stores an out-of-range `profile_scores.value` that `ai.calibration` clips (`score.ts:358`) but segments compare raw, and negative usage corrupts the monthly budget.
**Regression test:** malformed-response cases in `packages/ai/test/decision.test.ts`: probability `1.7`/`-0.7`, confidence `5`/`-1`, usage `-100`, distribution not summing to 1 (decide whether to enforce sum≈1 — recommend warn-only for the first patch to avoid breaking providers).

### #354 — P1 — Decision fetch bypasses the egress guard, unbounded read
**Confirmed.** `callSystemOne` (`decision.ts:247-258`) uses global `fetch` to `systemOneUrl(provider.baseUrl)` and `res.text()` with no byte cap; the 30 s `AbortSignal.timeout` bounds time, not size. `packages/ai/src` imports no `safeRequest`/`egressFetch`; the guard lives in `packages/integrations/src/egress.ts:254-287` and is threaded through `config.egress` (`apps/server/src/config.ts:331`) to webhooks, connectors, forms, warehouse, ads — but not to AI. `baseUrl` is `z.url().max(500)` (`providers.ts:186`) and settable via `aiProviders.create/update` (people-only, `workspace:admin` — `providers.ts:208-216,236-256`).
**Impact:** a workspace admin can point a decision provider at loopback/link-local/metadata/internal services and have the server POST there **with the provider API key in the Authorization header**, i.e. an SSRF + credential-leak primitive that bypasses the platform's own network boundary. A hostile provider can also return a multi-GB body.
**Regression test:** new egress test in `apps/server/test/decision-models.test.ts` (or `packages/ai/test/decision.test.ts` with an injected fetch policy): loopback `baseUrl` refused before any socket; oversized response aborted at the configured `maxBytes`. Assert the API key never leaves the process on a refused target.

### #355 — P2 — Reservation released before `ai_calls` is written
**Confirmed.** `decisionCall` (`decision.ts:298-305`) reserves, calls, and releases in `finally`. `usedThisMonth` counts `ai_calls` **plus live reservations** (`providers.ts:45-67`), and `reserveTokens` checks under a per-provider advisory lock (`:70-89`). Callers log afterwards: `score.ts:145` and `steps.ts:401` (which is after `finish`, whose own transaction can fail).
**Impact:** between release and insert a concurrent call sees neither, so the month can reach 2× the budget (the issue's example is exact); a failure after the provider call loses usage entirely.
**Regression test:** budget equal to one call, two concurrent `ai.score` calls in `apps/server/test/decision-models.test.ts`; assert exactly one succeeds and `ai.usage` never exceeds the budget. Also a `logCall`-throws case asserting the reservation is not silently dropped.

### #356 — P2 — Copilot turn can exceed its 20k reservation
**Confirmed.** `COPILOT_TURN_TOKENS = 20_000` (`copilot.ts:73`) is reserved up front (`:192`), but the turn runs `isStepCount(MAX_STEPS=12)` × `maxOutputTokens: 2000` (`:23,251-252`) → up to 24k output before prompt/tool/history tokens, and there is no per-step remaining-allowance cap. Usage is recorded (`:304-315`) then the reservation released (`:316`).
**Impact:** a turn whose budget check passed can overshoot the remaining monthly budget by its excess; a budget just above 20k does not stop the turn. Contrast: hosted runs already implement the correct pattern (`apps/server/src/agents/hosted.ts:299-312` caps each step at the remaining allowance and refuses a step below `MIN_STEP_TOKENS`).
**Regression test:** `apps/server/test/copilot*.test.ts` with a remaining budget of, say, 21k and a fake model that always produces `maxOutputTokens`; assert total recorded usage ≤ budget and the stream/loop stops when the allowance is exhausted.

### #357 — P1 — Missing tracking plan sends every trait
**Confirmed, reproduced.** `nonPersonalState` (`decision.ts:372-376`): with `plan === null` the trait filter is skipped entirely (`:376` passes `p.traits` raw). Nothing publishes a tracking plan at bootstrap (only reads: `artifacts/src/commands.ts:1702` is the getter); the plan type defaults `unknownTraits: 'store'` (`artifacts/src/types.ts:401-403`), and `traitClass` (`ingest/src/policy.ts:38-43`) keeps unlisted names out of the 11-name personal set as `'none'`. Repro: a free-text `notes` trait returns `null` from `personalDataIn`.
**Impact:** the **default** workspace state fails open: free-text, job titles, cities, dates of birth accumulate as plain traits and are sent to a provider with no ZDR, and the journey path persists the state in `ai_calls`. Only the regex sweep stands between this and the provider, and it does not see names/notes.
**Regression test:** `packages/ai/test/decision.test.ts` or an integration case: no published plan + a profile with `notes`/`job_title` → the request body contains an empty `traits` object (or the call is refused). Mirror the ingest default so "unlisted ⇒ non-personal" cannot leak.

### #358 — P1 — Decision state persisted in clear in `ai_calls`
**Confirmed.** `steps.ts:397` builds the call row with `stateHash`, but the `finish(...)` at `:401-415` passes `{ person: ready.state }`, and `finish` merges `person` into `input` (`:147`). `ai.calls` returns `r.input` raw (`packages/ai/src/commands.ts:84`) under `artifacts:read` (`:53`), so agent mandates holding that scope can read every scored person's full state. Docs promise the opposite twice (`docs/decision-models.md:118,181`) and the module comment repeats it (`decision.ts:22-23`). Note `ai.score`'s own `logCall` (`score.ts:208-212`) does the right thing — only the journey path is wrong.
**Impact:** contradicts a documented retention promise; traits, segment ids, event counts and the trigger are readable per person. Compounding with #352/#357 makes the stored state the only remaining copy of data the operator believed was never kept.
**Regression test:** in `apps/server/test/decision-models.test.ts`, run a decision node and assert `ai.calls { kind: 'score' }` has `input.stateHash` and **no** `input.person`.

### #359 — P2 — Expired-score retention missing; erasure claim rejected
**Partially confirmed after database-backed integration testing.** The initial source-only audit inferred no foreign key from `schema.ts`. The authoritative SQL migration `0064_decision_models.sql:30` already declares a composite profile foreign key with `ON DELETE CASCADE`, so erasure removes scores even without an explicit delete in `removeProfiles`. The erasure regression passes through that existing constraint.

Retention (`packages/audience/src/retention.ts`) does not prune `profile_scores` after `expires_at`, so expired derived data remains stored. That half is real and is fixed by bounded per-workspace hourly deletes using the existing workspace/expiry index. No orphan repair, foreign-key migration or duplicate erasure deletion is needed. The decision writer also rechecks the live profile under a row lock so an in-flight scoring request handles erasure gracefully rather than failing at the FK.

**Regression tests:** `apps/server/test/profile-scores-erasure.test.ts` verifies existing erasure cascading and expired-score deletion while retaining a live score. The decision-model suite verifies a write after erasure returns no stored score.

### #360 — P2 — Calibration turns a ClickHouse failure into "nobody converted"
**Confirmed.** `score.ts:327` `.catch(() => [])`; every derived number (`outcomes`, `positives`, `baseRate`, `brierScore`, reliability) flows from `events` (`:342-383`), and the output schema (`:277-294`) accepts the all-zero shape.
**Impact:** when ClickHouse is down, a documented pre-promotion check (`docs/decision-models.md:196`) returns a plausible report saying the model never predicts a converter — an operator may demote a well-calibrated model; nothing distinguishes it from a real result.
**Regression test:** `apps/server/test/decision-models.test.ts` with `events.conversionEvents` rejecting → expect a thrown error (or a new `status`/`error` field) rather than a zero report.

### #361 — P2 — `in` prototype keys
**Confirmed, reproduced.** `decision.ts:157-164` uses `label in probabilities` and `label in q.criteria`; both traverse `Object.prototype`, and `probabilities[label]` then yields a function, so `?? 0` never fires. Repro: `choice:'constructor'` accepted with `probability` of type `function`.
**Impact:** the broken answer is billed and logged `done`; `JSON.stringify` drops the function-valued probability so the journey interpreter's `typeof probability === 'number'` check (`journeys/src/interpreter.ts:324-328`) takes the fallback edge, and `storeProfileScore` fails writing a function to `double precision` (logged only). `ai.score` output validation then throws **after** `logCall('done')` committed.
**Regression test:** `packages/ai/test/decision.test.ts` — `choice:'constructor'`/`'toString'` must throw `invalid_response`; assert the picked probability is a finite number before the answer is returned.

### #362 — P2 — Stale claim blocks `agents.deleteHosted` forever
**Confirmed.** `deleteHostedAgent` (`packages/auth/src/hostedAgents.ts:359-366`) refuses on any `runningRunId`, with no `runningStartedAt` staleness check. The only takeover lives in `claimDue`'s claim update (`apps/server/src/agents/hosted.ts:478-495`), reachable only from the sweep of `enabled AND due` agents (`:665-671`) and the event sweep's `a.status = 'active' … AND (running_run_id IS NULL OR running_started_at < $2)` (`:694-710`). A disabled agent is selected by neither; a paused/revoked agent hits the not-active branch (`:457-475`), which inserts a skipped run and rolls `nextRunAt` but never touches `runningRunId`. `agents.updateHosted` does not clear it (`hostedAgents.ts:336-338`) and `agents.resume` refuses revoked (`packages/auth/src/agents.ts:267`).
**Impact:** a process killed mid-run leaves the claim; disabling/pausing/revoking then makes deletion permanently refused. For revoked there is no in-product remedy at all, contradicting `docs/agents.md:97`.
**Regression test:** in `apps/server/test/hosted-agents.test.ts`, set `running_run_id`/`running_started_at` older than `STALE_CLAIM_MINUTES`, then disable/pause/revoke and call `agents.deleteHosted` → succeeds (claim taken over or cleared).

### #363 — P2 — `finishRun` releases whatever claim is on the row
**Confirmed.** The update at `apps/server/src/agents/hosted.ts:402-415` never filters on `running_run_id` and writes `consecutiveFailures` from the claim-time snapshot. `STALE_CLAIM_MINUTES = 60` (`:25`) lets the sweep steal a still-running claim (`:478-495`); `createDb` is called without a statement timeout (`apps/server/src/app.ts:50`) and `finishRun`/`recordAiCall`/SMTP run outside the 120 s model timeout.
**Impact:** when a zombie run finishes it nulls the successor's claim and clobbers its failure streak; a third run can then start against the still-running second — duplicate sends/drafts, and a failure count that forgets the live run. Contradicts `docs/agents.md:90` ("a durable claim … is taken before the model is called").
**Regression test:** hosted-agents test that claims run A, backdates `running_started_at` past the stale window, lets a sweep claim run B, then finishes A → `running_run_id` must still be B's; A must not write `consecutive_failures`.

### #364 — P2 — Hosted runs offered tools they cannot use
**Confirmed.** `hosted.ts:255` builds the MCP server with `{ stepUp: true }`; `apps/server/src/http/mcp.ts:142` then lists every command whose permission `missingScope` says the principal's **role** could grant (`:83-87`), with the description at `:147-149` inviting the call. A hosted run has no OAuth step-up and no person to ask, so such a call can only fail — which the test at `hosted-agents.test.ts:225` already exercises ("refuses a tool call outside its scopes").
**Impact:** a viewer-sponsored agent sees all `artifacts:write`/publish tools and burns `maxToolCallsPerRun`/tokens on guaranteed failures; `docs/agents.md:84` says the opposite ("A tool outside them is not offered").
**Regression test:** assert `client.listTools()` for a hosted principal with a reduced scope set contains **no** tool whose required permission is outside those scopes, and that the docs sentence matches the chosen fix.

### #365 — P3 — Skipped event runs labelled `schedule`
**Confirmed.** Both skip inserts in `claimDue` (`hosted.ts:459-470`, `:500-508`) omit `trigger`, so `schema.ts:1392`'s default `'schedule'` applies. `claimDue` never receives the `RunOrigin` (signature at `:450-455`), so it cannot know. The event sweep filters `a.status='active'` (`:698`), but the gap between that SELECT and `claimDue` (pause/revoke, or a replica losing the claim race) still produces an event-origin skip.
**Impact:** audit-only: `agents.hostedRuns` misreports the trigger, contradicting `docs/agents.md:129`. No cap/retention effect (retention counts only `trigger='event'` rows, which is why the #342/#344 tests miss it).
**Regression test:** in `hosted-agents.test.ts`, pause the agent after `eventOrigin` and before `claimDue`, or force a lost claim on an event run; assert the skipped row carries `trigger: 'event'`.

1. **HTTP hardening — #347** (single file + middleware wiring in `app.ts`, tests in `body-limits.test.ts`). Cheapest, highest exposure; can ship alone first.

They share tests and the same threat model; splitting them risks reverting each other's helpers.
4. **Score integrity — #350 + #358** (both `steps.ts`/`storeProfileScore` contract; #351 is the natural third but is P2 — include it here if the batch can take one more change, since it edits the same call site and its test is the one #350 needs anyway).
5. **Memory authorisation — #348** (`hostedAgents.ts` + hosted-memory test).

Gate: `pnpm test`, plus the new body-limit, erasure, decision-privacy and memory tests. #352's fix must be merged with a decision on whether question text is redacted or dropped from `ai_calls` (dropping is simpler and matches the docs' "question set" wording less literally — recommend redacting with the same detectors and documenting it).
