## Verdict

**Not release-ready.** The five P1 gates from the previous review are genuinely closed — the fix is substantive, not cosmetic — but the new ownership/provenance layer that was added to close gate "shared-target/hash ownership" introduces **two silent-integrity holes** in exactly the place the report says is safe:

1. **P1-A — Meta's destination and remote-target identity include `adAccountId`, an optional connection setting that is not part of the Meta audience.** Two connections that reach the *same* custom audience therefore get different locks and different ownership scopes, and merely editing the setting evacuates and repopulates the live audience.
2. **P1-B — The ownership filter drops whole remove-sets (not the unowned keys) and finalization then deletes the ledger row *and* its durable intent.** An erased person's identifier can be left at the provider with no row, no intent, no `unresolved`, and an `ok` run.

Both are small, localized fixes (P1-A: build the Meta identity from `platform + audienceId` only; P1-B: filter removes per key and only delete an intent whose hashes were actually covered). Everything else is P2/P3.

## P1 findings

### P1-A — Meta identity is keyed on `adAccountId`, which is not part of the remote audience

**Code.**
- `refFromCurrent` (`packages/ads/src/audiences.ts:351-373`) sets Meta `operatingAccountId: settings.adAccountId ?? ''` (:355-357).
- That value becomes the persisted `destination_key` (`destinationKeyOf` :65-67) and the shared-target lock key (`remoteTargetKeyOf` :74-76, used at :1749-1778).
- `ownedElsewhere` compares `operating_account_id = ref.operatingAccountId` (:612, :622).
- The actual Meta call is `/{settings.apiVersion}/{ref.destinationId}/users` (:219) — **the ad account is never sent**; `adAccountId` is documented in the connector as "for spend import" and is **optional** (`packages/ads/src/platforms.ts:23-27`).

**Why it is wrong.** A Meta custom audience is identified by its audience id (authorization comes from the token). The ad account is not part of the remote target, so it must not be part of the identity used for locking, ownership, or "is this a different destination".

**(a) A settings edit wipes and repopulates the live audience.**
1. Sync S uploaded 40,000 people to audience `90000401` through connection C; `destination_key = meta:C:act_123:…:90000401`.
2. An operator enables spend import by adding `adAccountId: act_123` (or corrects it from `act_456` to `act_123`) — an unrelated field.
3. Next run: `currentKey` differs from `state.destinationKey` (:1607-1610), `listDestinationGroups` (:1560-1564) returns the old key as a *prior* destination, and `evacuateDestination` sends a `DELETE` to **the same audience id** (:219). Every member is removed (10,000 rows per run, :40-41).
4. Additions then re-add them at 10,000 per run (:1141-1197). Any interruption, rate-limit or flagged-audience error leaves the live audience partially or fully empty. `removed`/`added` report the churn as success; `docs/integrations.md:161` describes this as cleaning a *different* destination.

**(b) Concurrent runs can both skip a removal and both close their ledger rows (silent loss).**
1. Sync A uses connection `meta1` with `adAccountId` **unset** (`''` — the documented default); sync B uses `meta2` with `act_123`. Both target audience `90000401`, both contain profile P (`{email:E, phone:PH}`); both are healthy and published.
2. P is erased. `profiles.erase` deletes the profile row; both ledger rows remain.
3. A and B run at the same time. They compute different `remoteTargetKeyOf` values, so `withAudienceLocks` (:1717-1738) does **not** serialize them. A's `ownedElsewhere` finds B's row for P (`:615` excludes only the same sync) → `owned.profiles.has(P)` → **all of A's removes are dropped** (:754-759). B's read can happen before A's `finalizePlans` commits, so B also sees A's row and drops its removes.
4. Both then call `finalizePlans`, which deletes the rows whose plan is `final: null` (:646-661). Both runs report `status: ok`, `removed: 0`.

P's hashes remain in the audience with no ledger row, no intent, no `unresolved` and no error. The "one sync's cleanup cannot strand another's member" claim (`docs/integrations.md:166`) does not hold for Meta.

**Fix.** Give Meta a destination/remote identity of `platform + audienceId` (empty operating account and login account), or drop the ad account from both keys; keep the connection for credentials/provenance only. Add a test with two Meta connections (`adAccountId` set vs unset) on one audience and assert one lock, shared ownership, and no evacuation when only `adAccountId` changes.

### P1-B — Ownership filtering drops unowned identifiers, then deletes the row and the durable intent

**Code.**
- `writePlans` filters a *remove-set object* (`{email?, phone?}`) as a unit and drops the whole entry if **any** key is owned elsewhere (:754-759):
  ```ts
  remove: p.remove.filter((h) =>
    !owned.profiles.has(p.profileId) &&
    !(h.email && owned.hashes.has(h.email)) &&
    !(h.phone && owned.hashes.has(h.phone)))
  ```
- `finalizePlans` then deletes every plan with `final: null` (:646-661) and deletes **all** intents for the batch's profile ids, unconditionally (:704-717).

**Reproducible interleaving (identifier reassignment + erasure).**
1. Sync A has P in its segment and audience D, ledger `{email:E, phone:PH}`; the remote member is `(E, PH)`.
2. P is erased. `profiles.erase` deletes the profile and its identifiers (`packages/profiles/src/commands.ts:737`) and writes tombstones. Tombstones only block *late* events inside the grace window (`packages/profiles/src/resolve.ts:146-165`); a new identify after that is accepted, so E can come back.
3. E is identified again and becomes profile Q; Q consents and is added to sync B at the same destination D (B's row holds `{email:E}`).
4. A runs. The erasure plan is `remove: [{email:E, phone:PH}], add: null, final: null` (:1039-1079, :127-139). `ownedElsewhere` returns `hashes: {E}` because Q's row holds E. The whole remove-set is dropped.
5. `finalizePlans` deletes A's row. Result: **PH stays in Meta/Google permanently**, no row, no intent, `unresolved: 0`, and A reports `status: ok`.
6. Same with an ambiguous intent: an intent `{email:E, phone:PH}` for P (add applied, ledger write failed) is deleted at step 5 even though its removal was skipped, so the hash it was created to track is lost.

`docs/integrations.md:163` ("Nothing uploaded can become untracked") is therefore not true.

**Fix.** Filter per key, and send a remove for the keys that are not owned (a separate payload for the residual key if the batch schema needs it); alternatively, keep the row/intent with an explicit "partially owned" orphan reason instead of closing it. Delete an intent only when every hash in it was covered by a successful remove or by a live owner that still wants the member. Add a regression for (a) two profiles with partially overlapping identifier sets at one destination and (b) an ambiguous intent whose remove is skipped.

## P2 findings

### P2-1 — A disabled / unauthorized / unreadable connection does not mark the stored rows orphaned, so the erasure backlog under-reports

`loadConnection` (:338-349) returns `conn` **plus** an error for disabled, Google-not-connected and unreadable-secret cases. `fullPlatform` still resolves `current` from settings (`:1531-1540`), so it takes the `else if (currentError)` branch (:1604) which only records the error; the `markDestinationOrphaned` call sits only in the `!current` path (:1550-1558). Consequences:
- An erased person's row keeps `orphaned_at = NULL` and `destination_known = true`, so `countsFor.unresolved` (:1287-1309) and `audienceBacklog` (:2034-2118) do not show it; only the sync-level error text does. `ads.audiences` shows `unresolved: 0` next to the error.
- `docs/integrations.md:165` says the rows/intents "are kept and marked orphaned" for exactly these cases — the code does that only when the destination key cannot be resolved at all (deleted connection / unparseable settings).
- The new test at `apps/server/test/v074-audience-reconciliation.test.ts:463-480` asserts the error text and remote membership but never `unresolved`, so it does not catch this.

Fix: in the `currentError` branch, mark the current destination's rows/intents orphaned with the connection error as the reason (the `currentUnresolved` path already does this for deleted connections), and assert `unresolved > 0` in that test.

### P2-2 — The 500-syncs-per-round scheduler cap has no fairness or ordering

`runAudienceSyncRound` (:1851-1861) is `UNION … LIMIT 500` with **no `ORDER BY` and no persisted cursor**. The implementation report says "later sync ids wait for a later tick", but nothing guarantees rotation: the same plan-dependent prefix can be returned every tick, so on an install with more than 500 audience sync ids some syncs (and their erasure cleanups) can be starved indefinitely; a permanently failing sync also keeps consuming a slot. The return value (`{ syncs, failures }`) does not expose that rows were deferred. Fix: a keyset cursor over `(workspace_id, sync_id)` persisted across ticks (or `ORDER BY` + a saved last key), and report `deferred`.

### P2-3 — Merge repair removes the merged-away member without restoring the survivor in the same plan

`processMergeRepair` (:935-1037) re-points the row when the survivor has none, deletes a duplicate, and otherwise plans a removal of the merged-away row's hashes — with `current: null`, so `add` is null. The restore now comes from `processReconcile`'s match-bridge add, which works when the reconcile pass reaches the survivor **in the same run**. `reconcileProfileId` is a 10,000-row keyset (:1081-1139), so in an audience larger than that the survivor may not be visited this run: the merged-away remove can delete the survivor's remote member while the survivor's ledger still says present, until the cursor wraps (up to a full pass, hours). Fix: resolve the survivor in the merge plan and add the survivor's full current set there (the code already has the survivor id), rather than relying on a later pass.

### P2-4 — Acknowledging a legacy row for a still-consenting member is silently undone

`ads.acknowledgeAudienceCleanup` deletes the named legacy/intent rows and clears the obligation. If the person is a currently eligible segment member (the common case after an upgrade, where the legacy row was written to the same audience the artifact still targets), `processAdditions` has no current-key ledger row for them and re-uploads the hashes on the next run. The operator followed `docs/integrations.md:168` ("completes the manual removal out of band, then acknowledges") and the upload is immediately recreated with no new obligation. Erasure and withdrawal cases are fine (the profile is gone/not eligible). This is inherent to unknowable legacy provenance, but the doc must warn: acknowledging is "I checked this destination", not "delete the person", and a still-eligible member will be re-sent.

### P2-5 — `ads.audiences.cleanup` silently truncates at 200 sync ids

`cleanupSyncIds.slice(0, MAX_BACKLOG_PAGE)` (:1980) with no `next`/`total`/`deferred` field. Cleanup owed by a 201st unpublished/deleted sync is absent from the primary list; it is only reachable through `ads.audienceBacklog` (which is pageable). Either paginate this array or report the truncation. Also, `status: error` is derived from `unresolved` but `error` comes from the stored state, so immediately after the migration the entry can say `status: error, error: null` until the first run.

### P2-6 — Acknowledging cannot clear a combined error

`acknowledgeAudienceCleanup` clears the state only when `st.error?.startsWith(CLEANUP_PENDING_PREFIX)` (:2193). A run's error is a joined list (`[...errors, unresolvedText].join('; ')`, :1653-1656), so a state whose error is `removal failed: X; audience cleanup pending …` stays `status: error` with a stale message after the backlog reaches 0. Over-reporting, not under, but it makes "the acknowledgement closes the obligation" only half true until the next successful run.

## P3 / accepted limits (no action required for this release)

- **No keyset cursor for removals, evacuation or intent recovery** (`processRemovals` :1039-1079, `evacuateDestination` :816-846, `processCurrentIntents` :894-933). Failed rows keep their destination key, so a page of ≥10,000 permanently failing rows (the page caps) re-selects them every run and later rows in that sync wait. Bounded and visible via the orphan backlog; the report discloses the reconcile/add cursor tradeoff but not this one.
- **`MAX_PRIOR_DESTINATIONS = 50`** (:40): a permanently unreachable group occupies a slot. Acking the visible orphaned groups advances the queue, so there is a manual recovery path.
- **Orphan marking is write-amplified.** `markDestinationOrphaned` (:450-480) and `markProfilesOrphaned` (:482-535) rewrite `attempts`/`updated_at` on every tick for rows that will never change (65,536-row legacy groups were measured at 3.36 s). Consider `WHERE orphaned_at IS NULL` after the first mark, or bumping `attempts` only on an actual retry.
- **`saveState` writes `destinationKey: currentKey` even when the destination cannot be resolved** (:1604-1607, :1657), wiping the last known key, so a later `cleanupOnly` run cannot confirm/clear orphaned rows at that key. The rows stay orphaned (visible) and self-heal once the settings work.
- **Migration cost**: `cleanup_id uuid NOT NULL DEFAULT gen_random_uuid()` (0072:22, :59) is a volatile default, so it rewrites the table in addition to the explicit backfill `UPDATE` (0072:30-35). Fine at today's sizes; note it for large installs.
- **Merge chain longer than 20 hops** (:953-964) re-points to an intermediate profile. Extremely unlikely.
- **`audienceBacklog` ordering by random v4 `cleanup_id`** is a stable total order for paging but not chronological; newly orphaned rows can sort before the `after` cursor of an in-flight page. Standard for keyset paging; `total` still exposes the full count.

**Accepted as reported (verified in code / not re-run):** historical provenance is unknowable and is kept as an explicit obligation with a human ack; `legacy:unknown`/`destination_known=false` defaults make an old pod's insert an honest obligation (0072:13-19) rather than a failure; no `migrate.ts` drift beyond adding `0072 → 0.7.4`; the generated catalog (`/.claude/skills/agentic-marketing-mcp/references/tools.md`) matches the five commands and their permissions/humans-only flags; `newId` is `aud_` + 32 hex (`packages/core/src/ids.ts:7`), so the `syncId` regexes in the new commands accept real ids; the `created_at`/`updated_at` fix uses `new Date(...).toISOString()` (:2111-2112) and `lastRunAt` is a Drizzle `Date` (:1993, :2021).

## Security / tenancy checks

- `audience_write_intents` is created with `ENABLE`+`FORCE ROW LEVEL SECURITY`, a `tenant_isolation` policy on `current_setting('app.workspace_id')` and `GRANT SELECT, INSERT, UPDATE, DELETE … TO am_app` (0072:73-84); `audience_members` keeps its 0014 policy; the two backfills lift `FORCE` only around their own `UPDATE` (0072:27-35, :94-103) — required, because the owner is otherwise subject to the policy and `app.workspace_id` is unset during migration.
- All new reads/writes go through `db.withWorkspace` (RLS-scoped) except the round's cross-tenant discovery query (:1854-1861), which only lists ids, and the advisory-lock connection (:1717-1738), which uses no tables.
- Backlog/ack never expose hashes or profile ids; `last_error`/`orphaned_reason` contain provider messages, which contain hashes at worst, never plaintext identifiers.
- The ack's audit row stores only `input_hash` (`packages/commands/src/registry.ts:263, 394`), computed over the full input including the note, so the note is not retained.
- No HTTP inside a DB transaction anywhere in the new path; the advisory lock is taken on a dedicated session and released in `finally` with the connection destroyed if a release fails (:1717-1738).

## Test coverage assessment

Strong and honest where it matters: the fake provider models membership, not request counts (`apps/server/test/v074-…:38-52, 83-140`), so the shrink and merge assertions check the end state; DB-failure-after-apply and connection-drop-after-apply both assert the intent and the later erasure; unpublish/delete/disabled paths all assert remote membership plus the reported status. My independent trace of the merge case matches the parent's diagnosis: before `2a27f0a` the survivor's reconcile uploaded only `{email}` and created a second remote member; the match bridge makes it `{email, phone}`, which the fake attaches to the existing phone member, and the pure test was updated accordingly (16/16 pass locally).

Not covered, and where the P1 findings live:
1. two Meta connections on one audience with differing/missing `adAccountId` (lock, ownership, settings-edit evacuation);
2. partially overlapping identifier sets across two profiles at one destination, and an ambiguous intent whose remove is skipped by ownership;
3. `unresolved`/backlog after disabling a connection or disconnecting Google (only the error string is asserted);
4. >500 sync ids in a round (fairness), >10,000 rows in one removal page (progress), 201 cleanup sync ids in `ads.audiences`;
5. an acknowledgement followed by a scheduler round for a still-eligible member (re-add), and a combined error cleared by an ack.

## Bottom line

The redesign does what the three issues asked: destination provenance is immutable, a member-level removal restores the full identifier set, a durable intent makes ambiguous writes visible to erasure, cleanup no longer depends on publication, legacy obligations are inspectable and acknowledgeable, and the work is bounded and isolated. The one place where the new machinery over-reaches is ownership: it invents a Meta target identity from a setting that has nothing to do with the target (P1-A) and it closes rows/intents when it only *partially* skipped a removal (P1-B). Fix those two and the P2 items are ordinary follow-ups.
