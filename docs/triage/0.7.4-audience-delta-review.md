## P1-A — closed (evidence and re-checked interleavings)

- One identity for the target: `remoteTargetKeyOf` is `meta:<audienceId>` and `destinationKeyOf` is `<connectionId>:<remoteTarget>` (`audiences.ts:65-78`). `refFromCurrent` persists `operatingAccountId: ''` for Meta (`:353-363`); `adAccountId` is only parsed for validation and never sent (`:214-239`).
- Stored refs: members and intents are written with that same `operatingAccountId: ''` (`:557-560`, `:675-679`), so `listDestinationGroups`/`removeAllPlatform`/`cleanupOnlyPlatform` rebuild the identical key from stored columns.
- Locks: `storedAudienceState` maps stored rows through `remoteTargetKeyOf` (`:1744-1755`); `syncAudience` adds the same key for the current artifact (`:1802-1821`). Two Meta connections on one audience therefore share `audience-target:<ws>:meta:<audienceId>`.
- Ownership SQL: both the member and the intent half ignore `operating_account_id`/`login_account_id` for Meta and match on `platform + destination_id` (`:611-630`). The new `$n = 'meta'` predicate is type-safe (probed).
- Settings-only edit: `destinationKey` no longer moves when `adAccountId` is added/removed/changed, so `currentKey === state.destinationKey`, no prior group is created, and `state.error`/cursor are untouched. Test `v074-…:524-536` asserts zero requests to the audience and one remote member; pure test `reconciliation.test.ts:35-37` asserts key equality with and without the account.
- Re-checked prior P1-A(b): A (meta1, no account) and B (meta2, `act_…`) on one audience, both hold P, P erased. Both now take the same target lock (verified by the two-connection test at `v074-…:413-440`, which additionally shows the second sync is *skipped*, not raced). Whichever runs first sees the other's member/intent row as a full owner (hash match) and drops only its own row/intents; the second then sees no owner and removes. No both-drop.
- Residual (P3, by design, docs state it): `destination_key` still contains the connection for provenance, so an artifact *connection* change to the same Meta audience is still a prior destination and is evacuated (delete-then-re-add). Not a settings edit; accepted in the resolution. It is, however, the precondition for P2-B below.

## P1-B — closed for the named paths

- A plan is withheld from `safe` whenever one of its remove sets has `0 < shared < values.length` (`:756-771`); the member and its intent are marked orphaned with `audience cleanup pending: identifiers partially overlap…`, an error is pushed, and neither `finalizePlans` nor the intent delete runs for that profile (finalize is called with `safe` only, `:818`). Both tables keep the row, the intent and the backlog entry; `unresolved`/`ads.audienceBacklog` expose it. This is the "visible manual cleanup" requested; it does not demand automatic destructive removal.
- Fully shared sets: `send.remove` drops any set containing an owned hash (`:772-775`), and the plan is finalized, so the row/intent closes while the other owner's ledger keeps the coverage. Because a set is only sent when **none** of its hashes is owned, a sent remove payload cannot delete a remote member that another ledger still claims (any provider removal matches at least one payload hash).
- Mixed batches: a partial plan in a batch is excluded while the other plans in the batch still execute and finalize (`stopOnError` false paths: removals, intents, evacuation, merge). The one exception is P2-A below.
- Current-row vs intent: `planMemberWrite` emits the intent hashes into `remove` when they differ from current (`:137-152`), so an ambiguous intent is subject to the same partial check. Test `v074-…:538-584` covers `kind: 'member'` and `kind: 'intent'` separately and asserts error + `unresolved` + backlog kind + the remote member still present with its phone.
- Same-profile differing hashes: the old `owned.profiles.has(profileId)` short-circuit is gone; a profile-id match with disjoint hashes no longer suppresses the removal (correct per the resolution), and overlapping hashes suppress/retain by value. `owned.profiles` is now dead (P3).
- Tests are honest: the fake models membership, not request counts; the shared-ownership test uses two Meta connections at one audience (`:497-522`); the two-connection lock test is real; `maxReconcilePerRun: 0` isolates the merge restore (`:586-642`).

## P1-C — Merge restore overwrites the survivor's stored hashes and clears its obligation without planning their removal

**Code.**
- The restore is pushed as `{ profileId: survivor, remove: [], add: current, final: current }` (`audiences.ts:1033-1036`). `survivorRow.hashes` is read at `:992-1003` but only compared to the *merged-away* row for `sameHashes`; it is never passed as `stored`.
- `writePlans` then runs with `remove: []`, so the ownership/partial gate is bypassed, and `finalizePlans` upserts `hashes = excluded.hashes` and sets `orphaned_at = null, orphaned_reason = null, last_error = null` (`:693-704`) and deletes every intent for that profile at that key (`:707-718`).
- Order in `fullPlatform`: intents → **merge repair (`:1654`)** → removals → reconcile. So this runs *before* the reconcile that would normally remove the survivor's obsolete hashes.

**Interleaving A — silent untracked hash (the P1-B harm via another path).**
1. Sync S holds `{E1, PH1}` for profile P at destination X. Both identifiers are hashed for the platform.
2. P changes e-mail and phone (or the published artifact switches `identifiers` from e-mail to phone), so the current set `{E2, PH2}` is disjoint from the stored `{E1, PH1}`. The reconcile cursor has not reached P yet (10k/run on a large audience).
3. Another profile merges into P; the merged-away ledger row M exists at X.
4. `processMergeRepair` removes M's member and restores P with `final = {E2, PH2}`. `{E1, PH1}` is now in no row and no intent; the remote member keyed by `{E1, PH1}` is never removed. The later `processReconcile` sees stored == current and does nothing.
5. P is erased: the remove payload is `{E2, PH2}`, which does not match the `{E1, PH1}` member. It stays at the provider with **no row, no intent, no orphan, no `unresolved`, `status: ok`**.

**Interleaving B — obligation silently acknowledged.**
1. P's row is orphaned from a previous partial-ownership plan (or a disabled connection), i.e. a visible manual obligation.
2. A merge into P is pending at that destination.
3. The restore upserts P's row with `final = current`, clearing `orphaned_at/reason/last_error`, and deletes P's orphaned intent at that key. The operator never acked; the remote partial member remains. This contradicts "never blindly finalized".

**Trigger/limitation.** A merged-away ledger row for P at the current destination **and** (A) P's stored set differing from current, or (B) a prior orphan. Narrow, but silent in both cases; B directly defeats the delta's chosen safe behaviour.

**Fix (no destructive removal required).** Build the restore from the survivor's stored set and let the existing gate decide:
```ts
const planned = planMemberWrite({ profileId: survivor, current, stored: survivorRow.hashes, intent: null });
restores.push({ profileId: survivor, remove: planned?.remove ?? [], add: current, final: current });
```
- Stored == current → `planned` is null; the unconditional add is still done (needed because removing the merged member can delete the shared member).
- Stored != current → obsolete hashes are removed by the restore, partially shared ones are retained + orphaned by `writePlans`, exactly like any other write.
Also make sure `finalizePlans` does not delete an intent that the restore did not cover (or exclude a survivor with an orphaned intent from the restore and let the normal pass resolve it). Regression: merge with `maxReconcilePerRun: 0` where the survivor's stored hashes differ from current; assert the obsolete member is removed (or retained as a partial obligation), not forgotten; and a merge into a partial-orphaned survivor must leave the orphan marker and backlog entry in place.

## P2-A — A partial plan in `processReconcile` freezes the reconcile cursor and starves every later member

`writePlans` returns early on a partial plan when `stopOnError` is set (`:769`), and `processReconcile` passes `stopOnError: true` (`:1171`). `next` is then `outcome.lastOk ?? cursor` (`:1172`), and `lastOk` is the last *safe* plan of a previous batch. Interleaving: a current, consenting, in-segment member P is the first plan of the page and its obsolete set `{E1, PH1}` is partially owned (e.g. P's old e-mail was reassigned to another consenting profile and P's phone also changed). The obligation is recorded, but nothing in the batch is sent, `lastOk` is null, the cursor stays at the previous value, and P is re-selected first on every run. Every member with a larger `profile_id` is then never reconciled again (identifier updates, orphan clearing after a re-enable), indefinitely — visible as a permanent error, but silent for the starved members. `processAdditions` has its own cursor and is unaffected; `processRemovals` is unaffected because a leaver is not in the reconcile query.

Fix: on a partial plan, record the obligation and `continue` even when `stopOnError` (the plan is already excluded from `safe`); that lets the cursor advance past the obligation. Add a test with a partial *reconcile* (obsolete-hash) plan, not only an erasure plan.

## P2-B — Prior-destination evacuation can delete a member the same sync already re-added at the same remote target (pre-existing, but on the new shared-target path)

`ownedElsewhere` excludes `sync_id = syncId AND profile_id = ANY(ids)` regardless of `destination_key` (`audiences.ts:617` and `:627`). For a *same remote target* reached by a different connection (Meta: connection change, same `audienceId`; Google: two connections with the same `customerId` + list), the sync can legitimately have an old-key row and a new-key row for the same profile.

Interleaving:
1. Sync S targets audience X through connection C1; 30k members at key `C1:meta:X`.
2. The artifact is switched to connection C2 (same X). Old rows become a prior group.
3. Run 1: the evacuation's remove call fails (rate limit/flagged audience) → old rows are orphaned and kept, error reported; the run continues.
4. Same run: `processAdditions` sees those profiles have **no row at the current key** (only the old key) and adds them at `C2:meta:X`, writing new-key rows; the provider member is (re)created/attached.
5. Run 2: the evacuation retries the old rows. `ownedElsewhere` excludes the same sync's *new-key* rows for the same profiles, so the remove is sent, the provider member is deleted, and `finalizePlans` deletes the old rows. Additions now skip (new-key rows exist); reconcile sees stored == current and does nothing.
6. Result: the person is absent from audience X while the ledger says present, `status: ok` — a violation of P1 #1's "the ledger is not allowed to say a person is present when the provider removed them".

This exists before the delta, but the delta's "one Meta audience = one target" makes it concrete and it sits directly in the ownership layer being reviewed. Cheap hardening: scope the exclusion to the plan's own destination key, `NOT (sync_id = syncId AND profile_id = ANY(ids) AND destination_key = <destinationKeyOf(ref)>)`. Then a current-key row at the same remote target counts as the owner: the old remove set is fully shared → no remove is sent, and the old row/intents are dropped as covered; a partially overlapping set becomes a visible partial obligation. Rows at a genuinely different destination are already excluded by the `destination_id`/account predicate, so nothing else changes. Add a test with a connection switch to the same audience, a failed old removal and a successful add, then a retry.

## P3 / accepted residuals (not blockers)

- `destinationKeyOf` still includes `connectionId`, so a *connection* change to the same Meta audience evacuates and repopulates the live audience (interruption leaves it partially empty) even though the remote target is unchanged. Documented as provenance, accepted in the resolution; it is the precondition for P2-B.
- Stale comments: `ownedElsewhere`'s docstring still says ownership is checked "by profile id and by the actual hash values" (`audiences.ts:591-594`) and still returns an unused `profiles` set; `schema.ts:529-537` and migration `0072:2-4` still state that the Meta ad account is part of the immutable destination identity. These would invite the removed behaviour back; update them.
- `countsFor` counts an orphaned intent in both `orphaned` and `pending`, so `unresolved` can be 2 per obligation (`:1329-1343`, pre-existing).
- `cleanupTotal` counts sync ids while `cleanup` is per (sync, platform), so up to 2× entries; `cleanupAfter` is an unvalidated free string and is not mentioned in the command description (`:1988`, `:2040-2044`, `:2090-2091`).
- `roundCursors` is an in-process `WeakMap` (`:1895`): fair per instance, duplicated work when several replicas schedule, and a restart starts a new pass — all documented. The cursor does not skip a sync that is merely lock-skipped; it retries next pass.
- `processMergeRepair` now performs up to three extra queries (eligibility, membership, `profileForMessage`) per merged-away row inside one transaction (up to 1,000 rows), and each blocked partial plan opens its own `withWorkspace` transaction. Bounded, but heavier.
- `cleanupOnlyDestination` deliberately skips a merged-away intent (`:1281-1285`) without marking it orphaned; `unresolved` (which counts all pending intents) then shows an obligation that `ads.audienceBacklog` cannot list or acknowledge until the artifact is republished or deleted. Pre-existing, over-reporting only.
- `listAudiences` can show `status: error` with `error: null` immediately after migration until the first run (pre-existing).
- Orphan marking from a disabled connection rewrites `attempts`/`updated_at` every tick (accepted write amplification).

## Bottom line

P1-A and P1-B are closed as designed and the "visible manual obligation instead of a destructive removal" choice is implemented consistently and documented. The remaining blocker is P1-C: the newly added merge-survivor restore writes over the survivor's stored provenance and its orphan state without going through the same ownership/partial gate as every other write, which can still produce a remote identifier with no ledger, no intent, no backlog and an `ok` run. It is a narrow trigger but a small fix, and it is the one path in this delta that can silently defeat the guarantee the delta exists to provide. P2-A (reconcile cursor freeze) and P2-B (same-sync ownership exclusion across destination keys at one remote target) are ordinary follow-ups with concrete, small fixes.
