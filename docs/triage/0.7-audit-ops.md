## 1. Method and severity model

For every issue I re-read the cited code at HEAD (not the audit's line numbers, which drift), checked
callers and the surrounding contract/comment/docs, and reproduced behaviour where it was cheap
(#367 with a live `Intl` evaluation; #385/#387 by diffing `ENV_KEYS` against compose and `.env.example`).

Severity is assigned by **impact × reachability × detectability**, not by file location:

| Level | Meaning |
| --- | --- |
| **P0** | Active data-protection breach or remote unauthenticated availability loss on a **default** configuration; silent, no operator-visible signal. Ship first, out of band. |
| **P1** | Core function or documented guarantee broken, user-visible data loss, or a security control bypassable in a realistic self-host topology. Fix in the next patch release. |
| **P2** | Correctness bug with a scale, configuration or timing precondition; workaround exists or blast radius is contained. Next minor. |
| **P3** | Cosmetic / documentation-only with no functional consequence. Batch with other docs work. |

Classification note: issues labelled `documentation` on GitHub (#386, #387, #389, #391) are **not all
docs-only**. #389 carries a real install-ordering defect behind a wrong comment, and #387 hides
operator-critical keys. I split "label" from "what a fix must touch" below.

### P0 — ship as 0.7.1, out of band

#### #371 — Track-event properties are stored and exported verbatim without a tracking plan
**Label:** bug · data · **Confirmed**

- `packages/ingest/src/policy.ts:97-111`: `properties` is copied wholesale at :97; the **only**
  `delete properties[p.name]` (PII removal) is at :111, nested inside
  `if (plan && ... (e.type === 'track' | 'page' | 'screen'))` at :99. The branch requires a
  published plan.
- `packages/ingest/src/gateway.ts:160-165`: `plan: await publishedSingleton(tx, 'tracking_plan')` —
  `null` when nothing is published. `packages/ingest/src/policy.ts:15-18` sets the default policy to
  `{ plan: null, ... }`, so an unpublished workspace takes the untracked path for **everything**.
- Even with a plan, `unknownEvents` defaults to `'allow'` (`packages/artifacts/src/types.ts:367`), so
  an unlisted event keeps its properties and only emits a warning (:103-104).
- Sink: `packages/warehouse/src/datasets.ts:172-186` exports `toJSONString(properties)` and
  `toJSONString(context)` unmodified, contradicting `datasets.ts:5-7` ("Nothing here is personal data
  in the clear") and `docs/integrations.md:170` ("Personal traits stay behind … never exported").
- `packages/ingest/src/policy.ts:5-6` states the module's own purpose as "keeping personal data out of
  the event store" — the guarantee it breaks.
- Profile *traits* are handled correctly (`splitTraits` at `policy.ts:47-53`, used at :130), which is
  why the gap is easy to miss: only event `properties`/`context` leak.

**Why P0:** default configuration, no plan required, no operator signal, and the data lands in
Postgres/S3 outside crypto-shredding, the consent ledger and `profiles.erase`. Segment-spec
`track "Order Completed"` with `properties.email` is the canonical payload.

**Regression test** — `packages/ingest/test/policy.test.ts` (exists): add cases
(1) `plan: null` + `track` with `{ email, name, address }` → those keys absent from the returned
event, (2) plan present but event unlisted with `unknownEvents: 'allow'` → `properties` still
redacted, (3) a `pii: false` property survives. Extend `apps/server/test/phase10-warehouse.test.ts`
with an end-to-end assertion that an exported `events` row for a no-plan workspace contains no
configured personal keys.

#### #372 — A standing `ad_measurement` refusal is overridden by a per-event consent signal
**Label:** bug · data · **Confirmed**

- `packages/ads/src/clickIds.ts:48-52`:
  `if (basis === 'consent') return signal === true || (signal === undefined && ledger === 'granted');`
  A client-supplied `true` wins over **any** ledger value, including `withdrawn`.
- The signal is client-controlled: it comes from `context.consent.categoryPreferences.<purpose>` on the
  public ingest path (`consentOf(...)`).
- `packages/ads/src/hook.ts:23-25` uses the same predicate before persisting ad click ids, so the
  click id (gclid/fbclid) is stored even when the ledger says withdrawn.
- `packages/ads/src/conversions.ts:250-253` only blocks a refusal recorded **after** the event
  (`now.updatedAt.getTime() > Date.parse(c.at)`), so an older standing refusal never blocks the send.
- Contract: `docs/architecture/adr/0014-consent-channel-precedence.md:18` and `:24` list ad
  conversions among channel-less readers where "a refusal on any channel wins … err on the side of not
  processing". `packages/ads/src/audiences.ts:181-185` already does it correctly via ledger-first
  `consentStatusSql` — the inconsistency is within one package.

**Why P0:** a withdrawal is ignored and hashed e-mail/phone is uploaded to Meta/Google. Art. 7(3)
GDPR; irreversible third-party disclosure.

**Regression test** — `packages/ads/test/platforms.test.ts` (exists) or a new
`packages/ads/test/consent.test.ts`: table-driven `purposeHolds` cases
`(signal:true, ledger:'withdrawn') → false`, `(signal:true, ledger:undefined) → true` (current
behaviour preserved for never-recorded people), `(signal:false, ledger:'granted') → false`,
`(signal:undefined, ledger:'granted') → true`. Plus a `hook.ts` test that no identifier row is
written for `ledger: 'withdrawn'` + `signal: true`.

#### #388 — Helm checksum annotation hashes only the ConfigMap
**Label:** bug · operations · **Confirmed (impact corrected)**

- `deploy/helm/agentic-marketing/templates/deployments.yaml:24-26`: only
  `checksum/config: … /configmap.yaml | sha256sum`. No `checksum/secret`.
- `envFrom` pulls the Secret too (`deployments.yaml:49`), so Secret-only changes (rotated
  `MASTER_KEY`, added `METRICS_TOKEN`, `KEY_PROVIDER` move) do not alter the pod template.
- Rotation instructions that assume a rollout: `docs/deployment/kubernetes.md:83-85` ("then remove
  `MASTER_KEY` …"), with no `kubectl rollout restart` step.
- Correction: this does **not** leave the old key active for new writes — `storeTokens`/`seal` use the
  new `MASTER_KEY` after restart only. The real harm is that rotation silently does not take effect and
  the old key remains decryptable-in-use until someone restarts by hand.

**Regression test** — `apps/server/test/deploy-config.test.ts`: read
`templates/deployments.yaml` and assert a `checksum/secret` annotation exists alongside
`checksum/config` (same file-based style the suite already uses for ingress/values).

#### #376 — Concurrent token refreshes can brick rotating OAuth connections
**Label:** bug · operations · **P2 — impact overstated in the issue**

- `packages/integrations/src/oauth.ts:202-243`: `runTokenRefresher` selects due rows with a plain
  `SELECT` (:204-207) and refreshes them one by one (:208) with **no claim or lease**; `storeTokens`
  writes unconditionally, and `invalid_grant` marks `oauthStatus: 'error'` (:229).
- No `FOR UPDATE SKIP LOCKED`, unlike `packages/integrations/src/deliveries.ts:145-151`.
- **Correction:** the issue's stated trigger ("a normal `RollingUpdate` of the scheduler Deployment
  transiently runs two schedulers on every deploy") is **not true for the shipped chart**:
  `deploy/helm/agentic-marketing/templates/deployments.yaml:13-15` sets
  `strategy: { type: Recreate }` for the scheduler with the comment "never two schedulers at once",
  and `values.yaml:26` pins `replicas: 1`.
- Residual real exposure: any non-chart multi-replica deployment (Compose scaled to 2 with
  `ROLE=scheduler`, a bare-metal pair, a chart fork that drops the strategy), plus manual
  `kubectl scale`. Also the second half of the issue stands independently: on `invalid_grant` the
  loser overwrites the winner's freshly stored tokens because it never re-reads.

**Regression test** — `packages/integrations/test/` (new `oauth-refresh.test.ts`): run two
`runTokenRefresher` ticks concurrently against a rotating fake provider; assert only one POST per
connection per lease window and that the connection ends `connected` with the winner's tokens. A
`deploy-config.test.ts` assertion can pin the scheduler strategy/Recreate so the mitigation cannot be
removed silently.

beyond a lowered cap (make the cap injectable on the events interface), assert the result includes them
