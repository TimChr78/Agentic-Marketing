### 3.1 #392 — `reset()` leaves `am.uid` in storage — **P1, confirmed**

**Claim.** `persistIds()` only writes `am.uid` when a user id exists; it never removes a stale one while analytics stays allowed. `reset()` clears the in-memory id and calls it, so the value survives.

**Evidence.**

`packages/sdk-js/src/index.ts:166–176`:
```ts
const persistIds = () => {
  ...
  if (allowed()) {
    store.set(KEYS.anonymousId, anonymousId);
    if (userId) store.set(KEYS.userId, userId);   // :171 — no else-branch removal
  } else {
    store.remove(KEYS.anonymousId);
    store.remove(KEYS.userId);
  }
};
```
`packages/sdk-js/src/index.ts:326–331`:
```ts
reset() {
  anonymousId = uuid();
  userId = undefined;
  clickIds = {};
  persistIds();          // consent is unchanged; allowed() is still true
},
```
The reader at `:147` (`let userId = (allowed() && store.get(KEYS.userId)) || undefined;`) restores it on the next page load.

**Executed result** (`/tmp/am-repro-sdk.mts`):
```json
{ "storedUidBeforeReset": "alice", "storedUidAfterReset": "alice",
  "nextInstanceEventUserId": "alice" }
```
`reset()` is documented as "Forget the visitor on this device (e.g. on logout): new anonymous id, no user id" (`:325`); the code contradicts its own contract. This is the highest-severity SDK bug: post-logout events, including those of the next person on a shared device, are attributed to the previous account and can feed journeys, profiles and ad audiences.

**Fix sketch.**
```ts
if (allowed()) {
  store.set(KEYS.anonymousId, anonymousId);
  if (userId) store.set(KEYS.userId, userId);
  else store.remove(KEYS.userId);          // also covers identify(null)
}
```
Optionally make `identify(null)` an explicit "forget this user" as well.

**Regression test** — `packages/sdk-js/test/sdk.test.ts`, extend the existing reset-adjacent case:
```ts
it('forgets the user id on reset even while analytics stays allowed', async () => {
  const h = harness();
  const a = h.make();
  a.setConsent({ analytics: true });
  a.identify('alice');
  await a.flush();
  a.reset();
  await a.flush();
  expect(h.data.has('am.uid')).toBe(false);
  const b = h.make();                 // same storage
  b.track('After logout');
  await b.flush();
  expect(h.events().at(-1).userId).toBeUndefined();
});
```
Fails today at the first assertion (`am.uid` is still `"alice"`).

**Why CI is green:** the existing test at `sdk.test.ts:56` only checks `am.uid` removal when consent is flipped to `false`, which is the `else` branch; `reset()` is never tested.

### 3.2 #393 — queued events are sent after consent withdrawal — **P1, confirmed**

**Claim.** `setConsent` persists the new choice and flushes, but the outbox (events queued while consent was granted) is neither discarded nor re-checked. The retry path restores failed batches without consulting consent.

**Evidence.**

`packages/sdk-js/src/index.ts:264–276`:
```ts
setConsent(choice: Consent) {
  ...
  consent = { ...(consent ?? {}), ...choice };
  store.set(KEYS.consent, JSON.stringify(consent));
  persistIds();
  if (JSON.stringify(consent) !== before) enqueue({ type: 'track', event: CONSENT_EVENT, ... });
  const held = pending;               // pending only holds events queued while consent === null
  pending = [];
  if (allowed()) for (const e of held) outbox.push(...);
  void flush();                       // :275 — flushes outbox, which still holds pre-withdrawal events
},
```
Events are frozen with their consent snapshot at enqueue (`:197`: `context: { ...context(), ...(ev.context ?? {}) }`), so the surviving batch carries `analytics: true` even though the visitor has just said no.

Retry path, `:229`:
```ts
} catch {
  outbox.unshift(...batch.slice(0, MAX_QUEUE - outbox.length));   // no consent check
```

**Executed result** — the request after withdrawal contains the earlier event:
```json
[{ "event": "Segment Consent Preference Updated", "analytics": true },
 { "event": "Queued before refusal",            "analytics": true },
 { "event": "Segment Consent Preference Updated", "analytics": false }]
```
With a failing collector first (`503`) and consent withdrawn before the retry, `"Failed under grant"` is still transmitted after the withdrawal, alongside stale `analytics: true` consent events.

**Impact.** High: a refusal does not stop data already collected under the old grant from leaving the browser; a flaky collector can stretch the window across retries (backoff up to 60 s client-side). This is the second part of the same "consent is checked once" family as #405.

**Fix sketch.**
- Treat the tracking purpose as the purpose of every queued event (the SDK has exactly one: `opts.trackingPurpose ?? 'analytics'`).
- In `setConsent`, when that purpose flips `true → false`, drop `outbox` entries other than `CONSENT_EVENT` before flushing; keep the consent event.
- In `send()`/`catch`, drop any event whose purpose is no longer allowed before requeueing, so an in-flight failure cannot resurrect it.
- Keep the `consent: null` holding path (`pending`) unchanged.

**Regression tests** — `packages/sdk-js/test/sdk.test.ts`:
```ts
it('discards events queued under a grant when consent is withdrawn', async () => {
  const h = harness();
  const a = h.make();
  a.setConsent({ analytics: true });
  await a.flush();
  a.track('Queued before refusal');
  a.setConsent({ analytics: false });
  await a.flush();
  expect(h.events().map((e) => e.event)).toEqual(['Segment Consent Preference Updated']);
});

it('does not retry a failed batch after withdrawal', async () => {
  const h = harness(503);
  const a = h.make();
  a.setConsent({ analytics: true });
  await a.flush();
  a.track('Failed under grant');
  await a.flush();               // 503, requeued
  a.setConsent({ analytics: false });
  h.setStatus(200);
  await a.flush();
  expect(h.events().some((e) => e.event === 'Failed under grant')).toBe(false);
});
```
The `harness()` helper needs a mutable status setter (small local change).

**Why CI is green:** `sdk.test.ts:44` ("discards the queue on no") queues the event while `consent === null`, so it exercises the `pending` path, never the `outbox` path that this bug lives in.

### 3.3 #394 — rejected beacon loses the page-hide batch — **P2, confirmed**

**Evidence.** `packages/sdk-js/src/index.ts:236–243`:
```ts
function flushOnHide() {
  if (!outbox.length) return;
  const beacon = opts.sendBeacon ?? (navigator.sendBeacon?.bind(navigator));
  if (!beacon) return void flush();
  const batch = outbox.splice(0, 100);       // :241 — removed before the call
  beacon(endpoint, JSON.stringify({ ... })); // :242 — boolean result ignored
}
```
`sendBeacon` returns `false` when the browser refuses to queue the request (keepalive quota, oversized payload, shutdown), and the events are already gone from `outbox`.

**Executed result:** `{ "beacons": 1, "recoveredByFetch": false }` — after the rejected beacon, `flush()` sends nothing.

**Fix sketch.**
```ts
const batch = outbox.splice(0, 100);
if (!beacon(endpoint, JSON.stringify({ ... }))) {
  outbox.unshift(...batch);       // preserves order; the normal flush retries
  void flush();
}
```
Be aware that `flushOnHide` runs while `send()` may be in flight; `unshift` keeps ordering, and `flush()` is serialized by `sending`.

**Regression test** — `packages/sdk-js/test/sdk.test.ts`, driving the registered listener:
```ts

  let hide: (() => void) | undefined;

  (globalThis as any).document = { visibilityState: 'hidden', title: '', cookie: '' };
  let beacons = 0;
  const h = harness();
  const a = h.make({ sendBeacon: () => { beacons += 1; return false; } });
  a.setConsent({ analytics: true });
  await a.flush();
  a.track('Hidden event');
  hide!();
  await a.flush();
  expect(beacons).toBe(1);
  expect(h.events().map((e) => e.event)).toContain('Hidden event');
});
```
Needs the same global stubs the repro used; alternatively export `flushOnHide` behind a test seam.

### 3.4 #395 — identity merges discard the losing profile's topic opt-outs — **P1, confirmed**

**Evidence.** `packages/profiles/src/resolve.ts:248–306` (`merge()`) moves, in order: identifiers (`:258–274`), `journey_participants` (`:275–277`), holdout arms via `merge_holdout_assignments` (`:280`), traits/PII and timestamps (`:282–300`), deletes the source profile's key (`:299`), the profile row is tombstoned with `mergedInto` (`:296–300`), a `profile_merges` row is written (`:301`), source `consent_state` deleted (`:302–305`) and `recomputeConsentState` for the survivor (`:305`).

There is **no** statement touching `topic_preferences` anywhere in the file (grep for `topic` in `resolve.ts` returns nothing), and no trigger or FK cascade does it: `topic_preferences` is a plain table keyed on `(workspace_id, profile_id, topic)` with no FK (`packages/db/src/schema.ts:344–357`). The only merge helper that exists in migrations is `merge_holdout_assignments` (`packages/db/migrations/0041_holdout_assignments.sql:32`), which is the pattern to copy.

Reads only look at the survivor: `topicChoicesOf` filters `profile_id` (`packages/profiles/src/consent.ts:278–287`) and `effectiveTopicStatus` falls back to the topic default when no row matches (`:274–276`); `topicSubscribedSql` does the same in SQL (`:290–294`).

**Reproduction consequence:** B unsubscribes from a topic whose default is `subscribed`; B merges into A; A has no row; every send path that evaluates the topic for A gets `subscribed`. The person's explicit refusal is silently reversed. This is a direct-marketing violation, not a cosmetic data gap.

**Fix sketch.** Add migration `0042_merge_topic_preferences.sql`:
```sql
CREATE FUNCTION merge_topic_preferences(p_from text, p_into text) RETURNS void
LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
DECLARE ws uuid := nullif(current_setting('app.workspace_id', true), '')::uuid;
BEGIN
  IF ws IS NULL THEN RAISE EXCEPTION 'no workspace'; END IF;
  IF p_from = p_into THEN RETURN; END IF;
  INSERT INTO topic_preferences (workspace_id, profile_id, topic, status, source, updated_at)
  SELECT workspace_id, p_into, topic, status, source, updated_at
  FROM topic_preferences WHERE workspace_id = ws AND profile_id = p_from
  ON CONFLICT (workspace_id, profile_id, topic) DO UPDATE
  SET status = CASE
        WHEN excluded.updated_at > topic_preferences.updated_at THEN excluded.status
        WHEN excluded.updated_at = topic_preferences.updated_at
             AND excluded.status = 'unsubscribed' THEN 'unsubscribed'   -- opt-out wins ties
        ELSE topic_preferences.status END,
      source = CASE WHEN excluded.updated_at >= topic_preferences.updated_at THEN excluded.source ELSE topic_preferences.source END,
      updated_at = GREATEST(excluded.updated_at, topic_preferences.updated_at);
  DELETE FROM topic_preferences WHERE workspace_id = ws AND profile_id = p_from;
END $$;
REVOKE ALL ON FUNCTION merge_topic_preferences(text, text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION merge_topic_preferences(text, text) TO am_app;
```
Call it from `merge()` next to `merge_holdout_assignments` (`resolve.ts:280`). Document the conflict rule in `docs/identity.md` (most recent choice wins, opt-out wins exact ties). Keep `topic_preference_history` append-only; decide explicitly whether reads use the merged family (`profiles.mergedFrom`, as `profiles.export` already does at `commands.ts:597`) or history is repointed — the acceptance criterion is that evidence stays reachable.

**Regression test** — `apps/server/test/phase1.test.ts` (merge test at `:163`) or a new `apps/server/test/v030-merge-consent.test.ts`:
```ts
// topic default subscribed; B unsubscribes; merge B into A
await api.call('topics.set', { profileId: b, topic, status: 'unsubscribed' });   // resolves to the B profile
await send([{ type: 'identify', userId: 'u-a', anonymousId: 'anon-b' }]);        // triggers the merge
const prefs = await api.call('topics.preferences', { profileId: a });
expect(prefs.topics.find((t) => t.topic === topic)?.status).toBe('unsubscribed');
// and the send path agrees: a topic-targeted send to the segment containing A is skipped
// (reuse the staged-send helpers used by the broadcast tests, then assert A is not a recipient).
```
Add a second case with A and B both having rows, to pin the conflict rule and a repeated-merge case.

### 3.5 #396 — static and snapshot memberships stay on the merged-away profile — **P2, confirmed**

**Evidence.** Same `merge()` (`resolve.ts:248–306`) — no `segment_memberships` / `segment_list_members` handling. Both tables are keyed on `(workspace_id, segment_id, profile_id)` with no FK (`schema.ts:552–575`).

Refreshes cannot repair it:
- `refreshSegment` returns early for lists: `if (seg.definition.mode !== 'dynamic') { ...count... return }` (`packages/segments/src/membership.ts:160–168`).
- `streamUpdate` skips non-dynamic segments: `if (seg.definition.mode !== 'dynamic' || !seg.definition.condition) continue;` (`:253`; the same guard at `:277` for the consent-driven path).

So a static list keeps the tombstone profile id forever, and `segments.members` counts and returns it (`packages/segments/src/commands.ts:84–175`, filter is `segmentId` only), while the canonical person is absent. For dynamic segments the next refresh heals it, which is why the bug is list-specific.

**Fix sketch.** `merge_segment_membership(p_from, p_into)` in the same migration family:
```sql
-- list source of truth
INSERT INTO segment_list_members (workspace_id, segment_id, profile_id, added_at, added_by, source)
SELECT workspace_id, segment_id, p_into, added_at, added_by, source
FROM segment_list_members WHERE workspace_id = ws AND profile_id = p_from
ON CONFLICT (workspace_id, segment_id, profile_id) DO UPDATE
SET added_at = LEAST(segment_list_members.added_at, excluded.added_at);
DELETE FROM segment_list_members WHERE workspace_id = ws AND profile_id = p_from;
-- materialized membership
INSERT INTO segment_memberships (workspace_id, segment_id, profile_id, since)
SELECT workspace_id, segment_id, p_into, since FROM segment_memberships
WHERE workspace_id = ws AND profile_id = p_from
ON CONFLICT (workspace_id, segment_id, profile_id) DO NOTHING;
DELETE FROM segment_memberships WHERE workspace_id = ws AND profile_id = p_from;
```
Also ship a one-off repair for existing tombstones (join `profiles.merged_into` and re-point), otherwise deployments keep stale rows forever. Counts (`total`, `segmentRuns.members`) must be recomputed or derived.

**Regression test** — `apps/server/test/v028-audiences.test.ts` (list tests at `:64`, `:144`) and `phase2-segments.test.ts`:
```ts

await send([{ type: 'identify', userId: 'u-a', anonymousId: 'anon-b' }]);   // merge B into A
```

### 3.6 #397 — timestamp-only pagination silently omits tied events — **P2, confirmed (impact bounded)**

**Evidence.** Export paging, `packages/profiles/src/commands.ts:589–594`:
```ts
while (events.length < input.maxEvents && events.length % 500 === 0 && events.length) {
  const more = await profileEvents.handler(
    { profileId: profile.id, limit: Math.min(500, input.maxEvents - events.length),
      before: events[events.length - 1].timestamp },      // :591 — timestamp only
    ctx,
  );
  if (!more.events.length) break;
  events.push(...more.events);
}
```
and the store, `packages/events/src/clickhouse.ts:304–311`:
```sql
... FROM events FINAL
WHERE <id filter> AND timestamp < {before:DateTime64(3,'UTC')}
ORDER BY timestamp DESC LIMIT {limit:UInt32}
```
`profiles.list` has the same shape: `lt(schema.profiles.lastSeen, new Date(input.before))` with `ORDER BY lastSeen DESC` (`commands.ts:157–159`), so people sharing the boundary `lastSeen` are skipped on the next page.

**Impact.** Real but bounded: 500 events per page is well below the 100k cap, and equal-millisecond bursts come from imports, batch conversions and synthetic traffic. It is a DSAR completeness defect (Art. 15/20 export), not silent loss in the event store.

**Fix sketch.** Stable composite cursor, ideally opaque:
- ClickHouse: `ORDER BY timestamp DESC, event_id DESC` and `WHERE (timestamp, event_id) < ({before}, {beforeId})` (row-value comparison works in ClickHouse for tuples; if not, expand to `timestamp < b OR (timestamp = b AND event_id < bid)`).
- `profiles.list`: `ORDER BY lastSeen DESC, id DESC`, cursor `(lastSeen, id)`; keep accepting the old `before` for one release by treating it as `(before, 'ffffffff')`, then deprecate.
- Return the cursor in the output so clients never build it by hand (the current design forces clients/tests to echo the last item's timestamp).

**Regression test** — new `apps/server/test/v030-export-pagination.test.ts` (ClickHouse-backed through the harness):
```ts

await send(Array.from({ length: 501 }, (_, i) => ({ type: 'track', event: `E${i}`, userId: 'u-ties', timestamp: T })));
const { events } = await api.call('profiles.export', { profileId, maxEvents: 1000 });
expect(events).toHaveLength(501);
// and profiles.list does not skip people sharing lastSeen

```
(Exact call shape depends on the cursor field added by the fix.)

### 3.7 #398 — list commands disclose e-mail without a read audit — **P2, confirmed**

**Evidence.**
- `profiles.list` (`packages/profiles/src/commands.ts:116`) decrypts e-mail when `piiFilter(...)('email')` allows it (`:177–193`) and returns it (`:194`), but declares only `permission: 'profiles:read'`, `effect: 'read'` — no `auditReads`.
- `segments.members` (`packages/segments/src/commands.ts:84`) decrypts e-mail for a user principal with `profiles:pii` (`:130–152`) and returns it (`:169`), also without `auditReads` (`:102–104`).
- The executor audits a successful read only when the flag is present: `if (cmd.effect === 'read' && cmd.auditReads) await appendAudit(...)` (`packages/commands/src/registry.ts:405`).
- The audited peers do declare it: `profiles.get` (`commands.ts:230`) and `profiles.export` (`:580`).

This is a control gap, not an exposure: authorization is correct, only the trail is missing. It matters because `profiles.list` is the bulk path an insider or a compromised agent would use, and the product promises an audit trail for access to personal data.

**Fix sketch.** Prefer a conditional audit over unconditional (bulk reads would otherwise flood the hash-chained ledger with no-PII page views):
- extend the command definition to `auditReads: boolean | ((input, principal, output) => boolean)`, or add an `auditRead: 'pii'` marker that the executor resolves after the handler (it has `out` at that point);
- for both commands, audit when the response actually contained a non-null decrypted e-mail — `out.profiles.some(p => p.email)` / `out.members.some(m => m.email)`.

If the executor change is too much for a patch, ship `auditReads: true` now (correct, noisier) and refine later.

**Regression test** — `apps/server/test/v027-list-filters.test.ts` (profiles.list e-mail tests at `:98–125`) and `phase2-segments.test.ts`, mirroring `phase1.test.ts:252–257`:

### 3.8 #399 — `removals:false` suppresses consent-withdrawal removals — **P1, confirmed**

**Evidence.** `packages/ads/src/audiences.ts:181–203`:
```ts
const rows = await tx.execute(sql`
  SELECT m.profile_id, ${consentStatusSql(sql`m.profile_id`, 'ad_targeting')} AS status
  FROM segment_memberships m WHERE m.segment_id = ${def.segment}`);
const desired = new Set(rows.rows
  .filter((r) => purposeHolds(purposes, 'ad_targeting', undefined, r.status ?? undefined))
```

Because withdrawal removes the person from `desired`, and the only other escape hatch is erasure, `removals:false` also disables refusal removals. Exactly the third-party consequence the consent was supposed to prevent.

- The artifact schema documents the defective coupling as intended: `removals: z.boolean().default(true).describe('Remove people who leave the segment or withdraw ad_targeting')` (`packages/artifacts/src/types.ts:655`). The acceptance criteria require splitting these, so this description must change too.

**Fix sketch.** Compute both sets in the planning query, e.g. select `m.profile_id, status, true AS member` and build `inSegment`, then:
```ts
const eligible = new Set([...inSegment].filter((id) => consentOk.get(id)));
const removals = existing.filter((e) =>
  !alive.has(e.profileId) ||
  !eligible.has(e.profileId) ||                       // withdrawal/denial: always remove
```

### 3.9 #400 — destination change reuses the ledger and strands the old audience — **P1, confirmed**

**Evidence.**
- The destination is read from the current artifact content only: `ref` comes from `def[platform]` (`audiences.ts:174–179`), the connection at `:211`, and the call is built with the current `audienceId`/`userListId` (`:218–222`).
- The ledger key has no destination: `audience_members` PK `(workspace_id, sync_id, platform, profile_id)` and columns `hashes, added_at` only (`packages/db/src/schema.ts:522–534`).
- "Already uploaded" is therefore `have` keyed by `(syncId, platform)` alone (`audiences.ts:187–191`), so a republished artifact pointing at audience Y sees everyone as present and adds nobody (`:205`).
- Removals use the stored hashes but the **current** destination (`:222–240` → `call('remove', ...)`), so erasing a person deletes them from Y while X keeps their hashes.

Net effect: the new audience is empty and the old one can never be cleaned. Unrecoverable routing information is exactly what an erasure request needs.

**Fix sketch (requires a migration).**
- Add `connection_id` and `destination_id` to `audience_members` (and consider including them in the key, or keep the key and treat destination as reconciled state).
- On plan, compare stored `(connection_id, destination_id)` with the current ref. If they differ: remove from the old destination first (needs the old connection's secrets if it still exists; if it is gone, mark rows `orphaned` and surface a `ads.audiences` warning — never pretend it succeeded), then add everyone to the new destination.
- Backfill migration: for existing rows set the current destination (best effort) and document that pre-migration provenance is unknown.
- Interim mitigation: **none is safe without storage.** Operator guidance until the migration lands: never republish a changed destination under the same artifact id — create a new artifact and let the old one remove its members. Note this in the release notes.

**Regression test** — `apps/server/test/phase9-audiences.test.ts`:

### 3.10 #401 — identifiers never reconciled for an already-synced profile — **P2, confirmed**

**Evidence.** `packages/ads/src/audiences.ts:203–209`:
```ts
const adds = [];
for (const id of [...desired].filter((d) => !have.has(d)).slice(0, MAX_ADDS_PER_RUN)) {
  const person = await profileForMessage(tx, ws, id, deps.kp);
  if (!person) continue;
  const hashes = hashesFor(platform, person, def.identifiers);
  if (hashes.email || hashes.phone) adds.push({ profileId: person.id, hashes });

```
Only not-yet-uploaded profiles are hashed. Stored `hashes` (`schema.ts:529–530`) are never compared with what the current profile and `def.identifiers` would produce, and the insert is `onConflictDoNothing` (`:255–259`). Consequences: an e-mail change leaves the old hash at the platform; switching the artifact from e-mail to phone uploads nothing; dropping an identifier type never removes the already-uploaded value.

**Fix sketch.** Turn the loop into a reconcile per eligible member:
```ts
for (const id of [...desired]) {
  const current = hashesFor(platform, person, def.identifiers);
  const stored = storedByProfile.get(id);
  if (sameHashes(current, stored)) continue;
  // remove stored hashes that are no longer current, then add current ones
  changes.push({ profileId: id, remove: obsolete(stored, current), add: current });
}
```
Apply removes before adds per member (avoid a window with no identifier), keep provenance until the remote call succeeds (some platforms need separate add/remove batches — Meta's `users` endpoint supports both in one payload), and record both in the ledger row after success.

### 3.11 #402 — the run cap is applied before eligibility, so valid members can starve — **P2, confirmed (with an ordering caveat)**

**Evidence.** `packages/ads/src/audiences.ts:205`:
```ts
for (const id of [...desired].filter((d) => !have.has(d)).slice(0, MAX_ADDS_PER_RUN)) {
```
`MAX_ADDS_PER_RUN = 10_000` (`:23`). The cap is applied to *candidates*, before `profileForMessage`/`hashesFor` decide whether a usable identifier exists (`:206–209`). Skipped people are neither added to `have` nor remembered: nothing persists a scan position (`audienceSyncState` stores only counts/status, `schema.ts:536–545`), and the planning SQL has **no `ORDER BY`** (`audiences.ts:181–183`).

**Caveat on "permanently":** because the query is unordered, starvation depends on Postgres returning a stable row order for a stable plan — usual in practice, not guaranteed. The defect ("cap can starve eligible members and reports success") holds either way; the word "permanently" in the issue is a worst case, not a proof. Worth stating in the issue thread.

**Fix sketch.** Two changes, both cheap:
1. Filter for a usable identifier in SQL before the cap — join `identifiers` for `type IN ('email','phone')` (bounded by `def.identifiers`) so the 10,000 applies to actually addable people.
2. Add a keyset cursor (`lastProfileId`) to `audience_sync_state` and order by `profile_id`, so each run resumes where the last stopped and no one is skipped across runs even if some candidates fail to hash.

### 3.12 #403 — disabling edge mirroring leaves KV data and drops erasure deletes — **P1, confirmed**

**Evidence.**
- The erasure/queue gate requires **both** flags: `if (!(await enabled(ws))) return;` (`packages/personalize/src/edge.ts:198–199`) with `enabled` selecting `... WHERE workspace_id = $1 AND enabled AND snapshots` (`:190–195`).
- `deleteSnapshot` deletes locally, then awaits `queue(ws, ids, null)` under the comment "Erasure must reach the edge too: a failure here is an error, not a warning" (`:214–218`). With either flag off, `queue` returns silently, so the erasure **appears** to succeed while a remote copy survives (snapshot TTL is 30 days, `KV_SNAPSHOT_TTL_S`, `:25`).
- `syncEdge` cannot compensate: `if (!t?.enabled || !t.secrets || !t.secretsKeyId) return null;` (`:269`) and the scheduler only iterates enabled targets (`runEdgeSync`, `:363–368`). Disabling stops all cleanup.
- Bundle/experience/source puts carry **no** `expiration_ttl` (`:313`; only snapshots get one at `:329`), so write keys and experiences persist indefinitely. The edge worker reads the bundle and snapshots from KV with no knowledge of the target's current `enabled`/`snapshots` flags (`packages/edge-worker/src/worker.ts:98–117`), so stale data keeps serving.

This is the strongest "silent legal failure" in the batch: the caller is told the erasure happened.

**Fix sketch.**
1. **Separate cleanup from write gating.** A deletion must be queued whenever a remote copy *might* exist, independent of `enabled`/`snapshots`. Track `remoteKeys` (or a `pushed_snapshot_keys` table / KV list prefix) so `snapshots:false` can enqueue deletes for known keys; without tracking, use the Cloudflare KV list API on disable (`GET /keys?prefix=am:snap:`) inside the egress policy.
2. **Drain after disable.** `runEdgeSync` must also process targets with pending `edge_outbox` rows (or a `cleanup_pending` flag), not just `enabled` ones; only clear the flag when the outbox is empty.
3. **Fail closed on erasure.** If a target is configured but disabled and cannot be cleaned, `profiles.erase`/`deleteSnapshot` must surface a warning/error (or record a pending cleanup obligation), never return success silently.
4. **Optionally** set a TTL on source/experience keys too, or extend `pushedKeys` cleanup to cover all keys, so a workspace deleted without a disable drains eventually.

**Regression test** — `apps/server/test/phase11-personalize.test.ts` (fake KV records PUT/DELETE, `:55–58`; erasure test at `:138`; backfill at `:158`):
```ts

  await api.call('profiles.erase', { profileId: profileId!, reason: 'Erasure request (test)' });
  await eventually(async () => kv.has(`am:snap:${ws}:u:u-gold`), (has) => !has);   // fails today
  // and after full disable, a pending cleanup still drains
});
```
Add a second case asserting that disabling removes/expires the bundle and write-key entries (or that the worker no longer answers `edgeDecide` for that workspace).

### 3.13 #404 — changing the edge KV target does not restart the backfill — **P2, confirmed**

**Evidence.** `packages/personalize/src/edge.ts:131–140`:
```ts
const values = { accountId, namespaceId, apiBase, ...(snapshots !== undefined ? { snapshots } : {}),
                 ...(enabled !== undefined ? { enabled } : {}), ...(sealed ? {...} : {}),
                 // A new target gets everything again.
                 bundleHash: null, updatedAt: new Date() };
await ctx.tx.insert(schema.edgeTargets)
  .values({ workspaceId, ...values, backfillCursor: '' })        // :138 — insert only
  .onConflictDoUpdate({ target: ..., set: values });             // :139 — no backfillCursor
```
The comment promises a fresh-target backfill, but the conflict update never resets `backfillCursor`. `syncEdge` only backfills when `t.backfillCursor !== null && t.snapshots` (`:337–352`), so after the original cursor reaches `null`, pointing the workspace at a new account/namespace pushes the bundle and incremental snapshots but never replays inactive known people. Enabling `snapshots` from `false` has the same gap (`:305` guard also allows a no-op when the cursor is null).

**Fix sketch.** Read the current row first, then decide:
```ts
const [prev] = await ctx.tx.select().from(schema.edgeTargets).where(...);
const targetChanged = !!prev && (prev.accountId !== accountId || prev.namespaceId !== namespaceId || (prev.apiBase ?? null) !== (apiBase ?? null));
const enablingSnapshots = !!prev && !prev.snapshots && snapshots === true;
const resetCursor = !prev || targetChanged || enablingSnapshots;
... .values({ ..., backfillCursor: '' })
    .onConflictDoUpdate({ target, set: { ...values, ...(resetCursor ? { backfillCursor: '' } : {}) } });
```
Keep a secret-only rotation (same target) from rebuilding: it must not reset the cursor. Hash the target identity into a stored `targetHash` if you prefer not to compare fields.

**Regression test** — `phase11-personalize.test.ts` (backfill test at `:158`):

### 3.14 #405 — queued webhooks are sent after purpose withdrawal — **P1, confirmed**

**Evidence.**
- Purpose is checked **only at enqueue**: `if (ep.purpose) { ... if (!purposeAllowed(basis, state?.status)) continue; }` (`packages/integrations/src/webhooks.ts:298–303`), before inserting the delivery (`:308–325`) with `profileId`.
- The delivery worker re-reads only the endpoint's URL/secret/`enabled`: `if (!target) return { ok:false, permanent:true }` then sends `d.payload` (`packages/integrations/src/deliveries.ts:60–72`). `d.profileId` and `d.context` consent are available but unused.
- Retries span `WEBHOOK_BACKOFF = [10s, 60s, 5m, 30m, 2h, 6h, 12h]` (`deliveries.ts:26`), so a payload can leave **hours** after the refusal.
- Nothing cancels queued deliveries on `consent.record`; the consent command has no delivery hook.

**Fix sketch.**
- In `attempt()` for `kind === 'webhook'`, when `d.profileId` is set: resolve the canonical profile (follow `merged_into`, as `resolve.ts` does), load the endpoint's `purpose`, evaluate `purposeAllowed` against the **current** ledger, and return a non-sending outcome when disallowed.
- Add `'cancelled'` to `DeliveryStatus` (`schema.ts:950`) and set it with `response: { suppressed: 'consent' }`; the column is text-typed, so no DDL is needed, but the union and `deliveries.list` filters must accept it.
- Keep deliveries without a profile (ping/test, system events) untouched — the acceptance criterion says so explicitly.
- Optional efficiency: a `consent.record`/withdrawal hook cancels pending webhook deliveries for that profile in bulk, so the ledger does not accumulate doomed rows.

**Regression test** — `apps/server/test/phase5.test.ts` (webhook suite at `:95–140`; harness backoff is `[200, 200]`, `harness.ts:250`):

## 4. Cross-cutting observations

1. **Existing tests mask four of these bugs.**
   - `sdk.test.ts:44` exercises the `pending` (undecided) path, not withdrawal of already-queued `outbox` events (#393).
   - `sdk.test.ts:56` checks id removal only when consent flips to false, never `reset()` (#392).
   - `phase9-audiences.test.ts:223` tests withdrawal only with the default `removals: true` (#399).
   - `phase9-audiences.test.ts:220` asserts "second run adds 0" — true and desirable, but it also pins the absence of reconciliation unless the fixture changes identifiers (#401).
   - `phase5.test.ts:105` asserts a purpose-bound endpoint gets nothing when consent is absent *at creation*, not when it is withdrawn after queueing (#405).
   - `phase11-personalize.test.ts:138` tests erasure deletion only while snapshots stay enabled (#403), and `:158` tests backfill on a *fresh* configure/explicit sync, not a target change (#404).
2. **Consent is enforced at one point in time in two separate pipelines** (client outbox, server webhook deliveries). A shared "re-check eligibility immediately before egress" rule would close #393 and #405 together and prevent the next variant.
3. **Merge completeness is ad hoc.** `merge()` moves identifiers, journeys, holdouts, traits/PII and purpose consent, but not topics or segments. The existing SQL helper (`merge_holdout_assignments`) is the right pattern; the gap is process, not tooling. A merge checklist in `docs/identity.md` plus a test that enumerates every profile-keyed table would prevent #395/#396 class regressions.
4. **Destinations are not modelled as state.** #400 and, partly, #401/#402 stem from `audience_members` being a "who did we send" ledger without *where*. Adding provenance is a migration, not a patch.
5. **CI's audit gate is moderate-only**, so low advisories accumulate without disposition (#406). The fix is a documented low-severity review, not a lower threshold.
