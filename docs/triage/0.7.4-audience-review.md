# Independent review — 0.7.3 audience reconciliation (#400/#401/#402)

**Review type:** read-only. No edits, commits, pushes, issue/PR mutations, subagents, or server Vitest.
**Tree:** `/mnt/user/appdata/t3code/Agentic-Marketing`, branch `fix/0.7.3-execution-integrity`, uncommitted audience diff.
**Method:** full read of `packages/ads/src/audiences.ts`, migration `0071_audience_reconciliation.sql`, the audience tables/FKs/RLS in `0014_ad_audiences.sql` and `schema.ts`, the new server/package tests, `docs/integrations.md`, `docs/triage/0.7.3-bugfix-plan.md`, plus the artifact lifecycle, connection update, merge, erasure and scheduler paths. Primary provider docs checked (URLs in §1). Parent-reported test results (25/26 initial, 13/13 after fixture fix) are accepted; I did not run server Vitest.

## Verdict

**Not release-ready as-is.** The destination-provenance design is sound, but five issues are release blockers, and the legacy-cleanup recovery path is not actually implemented:

1. **P1 — Identifier shrink silently removes the person from the remote audience while the ledger records the remaining identifier as present.** The new tests encode the wrong provider expectation.
2. **P1 — A confirmed or ambiguous remote add/update can become untracked after a DB failure or timeout, so a later erasure cannot remove it.**
3. **P1 — Unpublishing (or otherwise removing) the sync artifact stops all cleanup; erasure/consent obligations are stranded with no scheduler, command, or `ads.audiences` entry.**
4. **P1 — `markOrphaned` binds every profile id of a group; a group above PostgreSQL's 65,535 bind limit throws, aborts the whole scheduler round, and can permanently block later syncs.**
5. **P1 — Legacy `legacy:unknown` rows have no inspect/acknowledge/recovery API; disclosure alone does not let an operator "confirm or complete" the cleanup as the docs claim.**

Remaining meaningful concerns: mutable connection settings are not part of provenance, `unresolved` is not exposed by `ads.audiences` at migration time, the ledger is not actually bounded in memory, and hash ownership is not modelled across syncs/merges.

## 1. P1 — Identifier shrink drops the remote member; ledger then lies

**Code path.** When the artifact narrows identifiers (`['email','phone']` → `['phone']`), `planPlatform` computes `remove = { email }` and `add = {}` (`packages/ads/src/audiences.ts:414-419`, helpers at `:40-53`). `syncPlatform` sends the email-only removal (`:697-704`), sends no add (`:705-712`), then writes the ledger as `{ phone }` (`:527-552`, called at `:713`). On every later run `sameHashes` sees `{phone}` = `{phone}` and does nothing (`:408-412`), so the missing member is never restored.

**Why this is wrong.** Both providers remove an audience **member/user**, not one stored identifier:

- Meta's own API reference for `/{custom_audience_id}/users` says under **Deleting**: “You can dissociate a User from a CustomAudience by making a DELETE request…”, and the payload is “users to delete” (multi-key only changes how the user is matched). <https://developers.facebook.com/docs/marketing-api/reference/custom-audience/users/>
- The Meta guide's **Remove Members** section likewise describes deleting users, with `EXTERN_ID` as an alternative way to “remove people”; it does not describe retaining a person by another identifier. <https://developers.facebook.com/docs/marketing-api/audiences/guides/custom-audiences/v25.0/>
- Google Data Manager `audienceMembers:remove` “Removes a list of `AudienceMember` resources”; an `AudienceMember` is “The audience member to be operated on”, and `UserData` “represents a single user” with one or more identifiers. <https://developers.google.com/data-manager/api/reference/rest/v1/audienceMembers/remove> <https://developers.google.com/data-manager/api/reference/rest/v1/AudienceMember>
- Google's Customer Match guide says “Remove specific users: Remove individual users from a list based on their identifiers” and “A `UserData` object represents a single user and can contain multiple user identifiers.” <https://developers.google.com/google-ads/api/docs/remarketing/audience-segments/customer-match/get-started>

There is no documented “delete only the email key and keep the phone key” operation. The test's assumption that the unchanged phone stays is therefore unsupported by the primary docs.

**The tests pin the bug.** `apps/server/test/v073-audience-reconciliation.test.ts:289-300` asserts “the unchanged phone stays” and requires exactly one POST (“only the original add”). `packages/ads/test/reconciliation.test.ts:26-29` asserts `addedHashes(...) === {}` for the shrink case. The loop therefore passes while the remote member is gone. The fake platform server only records requests (`v073…test.ts:27-46`); it does not model audience membership, so it cannot catch the end state.

**Fix direction.** For every reconcile row whose `remove` is non-empty, re-add the full current hash set (not only `addedHashes`). That is idempotent, restores the member, and also repairs the “phone was never re-sent after the first removal” state. Update both tests to model or assert the postcondition, not the absence of a second POST.

**Interleaving.**
1. Artifact allows `['email','phone']`; member added with both; ledger `{email,phone}`.
2. Publish `identifiers: ['phone']`.
3. Run: Meta/Google receive email-only DELETE and remove the user; ledger is updated to `{phone}`.
4. All later runs: stored `{phone}` = current `{phone}` → no add. Member permanently absent while `ads.audiences` reports `members: 1`.

## 2. P1 — Confirmed (or ambiguous) remote writes can become untracked

**Add path.** The remote add succeeds at `audiences.ts:723-726`; only then does `insertMembers` write the ledger (`:732`, `:554-584`). If the insert throws (DB outage, timeout, RLS/serialization error), the remote hash is not in `audience_members`. The function does not catch or compensate; the rejection escapes `syncPlatform` and is caught only by the whole-round handler at `:913-915`. If the profile is erased before a later successful insert, it is no longer selected by the additions query (`:434-452`), so the remote hash is never removed.

**Reconcile path.** The remove (`:698`) and add (`:706`) both succeed, then `updateReconciledHashes` writes the ledger (`:713`, `:527-552`). If that write throws, the ledger still holds the old hashes. A later erasure removes the old hashes, not the newly uploaded ones; the new hash is untracked. A batch failure amplifies this across every row in the batch.

**Timeout ambiguity makes it worse.** `call(...).catch(...)` at `:698`/`:706`/`:723` treats a timeout/5xx as “not applied”. The provider may have applied it. If the profile's identifiers change again (or the profile is erased) before the retry, the retry removes the ledger's old hash and adds the new current hash; the timed-out hash was actually uploaded and is never recorded.

This directly contradicts “An erasure removes the person from every destination this sync recorded” (`docs/integrations.md:163`): the destination recorded is not the full set of attempted writes.

**The new test does not cover it.** `v073…test.ts:500-530` holds the add, erases, releases, and lets the insert succeed; the next run removes the stored hash. That is the happy path. There is no DB failpoint after the remote call, and no timeout-after-apply case.

**Fix direction.** Record an intent/pending hash set **before** the HTTP call (same DB, durable), clear it only after the confirmed write is recorded, and have erasure/sync consider pending intents. Alternatively use a durable outbox. At minimum, on insert/update failure after a confirmed add, compensate with a remove and surface the failure; do not leave the hash untracked. Add a regression that fails the DB write after the fake platform accepts the add, then erases, and asserts a later run removes the hash (or that the intent is visible).

## 3. P1 — Unpublished/deleted artifacts strand erasure/refusal cleanup

**Evidence.**
- Scheduler candidates: `SELECT DISTINCT workspace_id FROM artifacts WHERE type='audience_sync' AND published_version IS NOT NULL` — `audiences.ts:908-912`.
- `publishedSyncs` is an inner join on `published_version` — `:888-901`.
- `ads.syncAudience` only searches `publishedSyncs` and returns `not_found` otherwise — `:995-996`.
- `ads.audiences` only lists `publishedSyncs` — `:953-956`.
- `unpublishArtifactVersion` sets `publishedVersion = null` and does not touch `audience_members`/`audience_sync_state` — `packages/artifacts/src/commands.ts:233-245`. (The normal path is `agents.undo`; direct deletion of the artifact leaves the same orphaned tables, and workspace deletion cascades the ledger away without touching the remote platform.) There is no foreign key from `audience_members`/`audience_sync_state` to `artifacts`; the only FK is `workspace_id → workspaces ON DELETE CASCADE` (`packages/db/migrations/0014_ad_audiences.sql:6-21`).
- The implementation report itself admits unpublished/deleted artifacts are not swept.

**Interleaving.**
1. Sync S adds P (ledger row + remote hash).
2. S is unpublished (e.g., an agent-published sync is undone), or the artifact row is deleted.
3. P is erased. `profiles.erase` succeeds and records the erasure; the audience ledger row is untouched (`packages/profiles/src/commands.ts:774-778`).
4. Scheduler skips S; `ads.syncAudience` says `not_found`; `ads.audiences` does not list S; no cleanup command exists.
5. The remote platform keeps P's hash indefinitely. The same applies to an ordinary leaver/withdrawal while unpublished.

There is also a race: scheduler reads a published `def`, the artifact is unpublished, then the in-flight `syncAudience` still adds people using that `def`; because the artifact is now unpublished, no later run cleans them.

The report's reason for excluding this (“avoid deleting platform audiences when an operator merely unpublishes to edit”) is reasonable as a design choice, but it leaves a legal erasure obligation without a trigger. At minimum there must be a visible cleanup queue and an explicit operator command; better, sweep state rows for non-published artifacts (with a documented grace/confirm step) or require an explicit “stop sync and clean” action.

**Missing tests:** unpublish after an add, then erase/withdraw, assert cleanup and visibility; scheduler round with only unpublished syncs; config change + unpublish during an in-flight run.

## 4. P1 — `markOrphaned` exceeds the bind limit and poisons the round

`markOrphaned` uses `inArray(schema.audienceMembers.profileId, profileIds)` with the **entire** group (`audiences.ts:500-525`, `:520`). It is called with all ids for a prior group at `:606`, `:612`, `:618`, `:627` and `:639`. Drizzle 0.45.4 `inArray` expands an array to one bind parameter per element (`node_modules/.pnpm/drizzle-orm@0.45.4…/sql/expressions/conditions.js:73-80`); PostgreSQL rejects a statement with more than 65,535 bind parameters.

**Concrete failure.** Upgrade a workspace with >65,535 pre-0.7.3 members: migration marks them all `legacy:unknown`; the first sync groups them as `prior`, calls `markOrphaned` with all ids, and throws. `syncPlatform` rejects; `runAudienceSyncs` catches at the round level (`:913-915`) and aborts all remaining workspaces/syncs for that tick. The same happens for a prior destination whose connection was deleted/disabled with >65,535 rows. The sync cannot reach the new destination population step, and every 15-minute round repeats the failure, starving later syncs.

`deleteMembers` is safe (batch of 1000, `:483-498`), and `insertMembers` is batch-sized; the orphan path is the outlier. Fix: chunk `markOrphaned` by `BATCH` (or use `= ANY($1::text[])`) and catch per sync so one poison sync cannot abort the round. Add a test with 65,536 legacy rows (or a unit test on the generated SQL) and a two-workspace round proving isolation.

## 5. P1/P2 — Legacy unknown rows have no recovery/acknowledgement path

Migration 0071 marks every pre-0.7.3 row `legacy:unknown`, `destination_known=false`, `orphaned_at=now()` (`0071_audience_reconciliation.sql:16-26`). On each run the loop marks them again and reports “cleanup pending … their destination was not recorded” (`audiences.ts:605-608`). The state row gets `unresolved` (`:772`, `:814`).

But:
- `ads.audiences` has no `unresolved` field (`SyncOut` at `:930-937`; mapping at `:968-976`), and no per-row/destination detail.
- There is no command to inspect or acknowledge the rows: `adAudienceCommands` contains only `listAudiences` and `runAudienceSync` (`:1014`).
- `profiles.erase` returns success without any audience/legacy check (`packages/profiles/src/commands.ts:774-778`), so the erasure ledger says the person was erased while an unknown remote copy remains.
- `docs/integrations.md:168` says “only an operator can confirm or complete the removal”, but nothing in the API lets an operator do that; even after manually purging the platform, the row keeps the sync in `status: "error"` forever.

This is materially weaker than the 0.7.2 warehouse precedent, which has `warehouse.erasureBacklog` (inspect, page, no identifiers) and human-only `warehouse.acknowledgeErasures` with a required note and audit (`docs/triage/0.7.2-bugfix-plan.md:34`, `docs/integrations.md:192`). Disclosure in a doc is not sufficient for an erasure obligation that cannot be closed or recorded.

**Recommended minimum:** a human-only `ads.audienceBacklog` (sync, platform, destination key/reason, counts; never raw hashes) and `ads.acknowledgeAudienceCleanup { ids, note }` that removes the selected orphan obligation and audits the note; and make the erasure result/status reflect an outstanding audience cleanup until acknowledged. This is analogous to, not identical to, the warehouse backlog because the destination is unknown; an acknowledgement is the only possible closure when the operator has handled it out-of-band.

## 6. P2 — Connection settings are mutable but not part of destination provenance

The destination key is only `<connection_id>:<destination_id>` (`audiences.ts:31-33`). The connector call uses the connection's **current** settings:

- Meta: `settings.apiBase`, `settings.apiVersion` (`:112-119`); the ad-account setting is not used for audience calls.
- Google: `settings.customerId` / `loginCustomerId` (`:140-161`, especially `:160-161`).

`connections.update` replaces settings wholesale (`packages/integrations/src/connections.ts:185-220`, `:205-214`) and does not check whether audience ledgers reference the connection. Google `productDestinationId` is “the ID of the audience in the `operatingAccount`” (<https://developers.google.com/data-manager/api/devguides/audiences/send-audience-members>), i.e. scoped to the account.

**Interleaving.** Sync Google connection C with `customerId=111`, list `700001`; ledger stores `C:700001`. An admin edits C's settings to `customerId=222` (or rotates credentials to an account with access only there). A later erasure/cleanup sends `operatingAccount=222, productDestinationId=700001`:
- if list `700001` does not exist there, the call fails and the row is orphaned (old copy remains, at least visible);
- if a different list `700001` exists there, the call succeeds, the run reports cleanup done, and the person is still in account 111's list.

Meta is less exposed because audience ids are globally unique; a token/API-base change either reaches the same node or fails. Google is the concrete risk. Fix: include an account/settings fingerprint (at least Google `customerId`/`loginCustomerId`) in the destination key/provenance, or refuse `connections.update` of those account fields while audience rows reference the connection, or store and verify a snapshot. Add a test that changes `customerId` without republishing and asserts the cleanup does not claim success against the new account.

## 7. P2 — Migration “surface immediately” claim is false

The migration comment says the legacy cleanup is surfaced “immediately, before the next scheduler/manual run” (`0071_audience_reconciliation.sql:41-50`), but it only writes `audience_sync_state.unresolved`; it does not set `status`/`error`, and `ads.audiences` neither selects nor returns `unresolved` (`audiences.ts:930-937`, `:954-976`). Immediately after upgrade, an existing platform still shows `status: "ok"`, `error: null`, with the unresolved count invisible. If the artifact is never run (unpublished, scheduler disabled, no tick), the cleanup is never surfaced at all.

Fix: expose `unresolved` in `SyncOut` and `ads.audiences`, or derive `status: "error"` from it at read time. Add an upgrade test that applies 0071 to a 0.7.2-shaped row and calls `ads.audiences` before any sync.

## 8. P2 — The planning read is not bounded; large ledgers can OOM

`planPlatform` loads **every** audience member row for the sync/platform, including `hashes`, into memory (`audiences.ts:280-283`), maps every profile id (`:287`), and passes the entire array as a single parameter to two queries (`:291-298`). The additions and reconcile pages are bounded, but the existing ledger and prior groups are not. A million-member audience means a million jsonb rows and a very large text array in one transaction; this is a memory/latency risk, not a bind-limit issue. `markOrphaned` is the bind-limit issue above.

Fix: aggregate counts/groups in SQL, select only the columns needed, paginate by profile id (keyset), or use a temp table for the id set. The report's claim “only the existing ledger rows and one bounded page are read” is technically true but not a bound.

## 9. P2 — Hash ownership is not modelled across syncs or merges

- **Two syncs, same destination.** The publish validator only checks connection type (`audiences.ts:55-75`); nothing prevents two `audience_sync` artifacts from targeting the same Meta audience/list. Each has its own ledger and its own advisory lock (`:833`). If P is in both segments, both add the same hash. P leaves S1's segment; S1 removes the hash and deletes its row. S2 still has P and stored hash = current hash, so `sameHashes` (`:408`) makes it do nothing; P is silently missing from S2's audience while S2 reports `members` including P.
- **Identifier reassignment / two rows with one hash.** `identifiers` has PK `(workspace, type, value)` (`schema.ts:267-279`), so two live profiles cannot share an email/phone at the same time. But after an identifier changes (the new test does exactly this by deleting the old email, `v073…test.ts:329-336`), the old value can be claimed by another profile while the first ledger still holds the old hash. A removal for the old profile then removes the new profile from the shared destination; the new profile's ledger still says present and its reconcile sees `sameHashes`, so it is never re-added.
- **Merge.** `merge` deletes the merged-away profile's `consent_state` (`packages/profiles/src/resolve.ts:311-313`) and moves identifiers/memberships, but does not touch `audience_members`. The merged-away ledger row becomes ineligible and is removed on the next sync; its stored hashes may match the survivor's remote member. Reconciliation is ledger-local and only re-adds `addedHashes`, so the survivor can be removed without a compensating add. `profileForMessage` follows `mergedInto` (`packages/profiles/src/commands.ts:807-817`), so the current hashes can also differ from the ledger key in ways the tests do not cover.

Fix direction: maintain hash ownership/refcounts per destination (or dedupe removals across all ledgers that target the same destination), forbid duplicate destination syncs or document/handle them, and reconcile `audience_members` on profile merge. Add tests for (a) two syncs to one audience, (b) identifier reassignment across profiles, (c) a merge with both profiles in the segment.

## 10. Minor / release-hygiene observations

- The implementation report says `migrate.ts` was intentionally not edited, but the working tree adds `'0071_audience_reconciliation.sql': '0.7.3'` (`packages/db/src/migrate.ts:102`). That is fine for the release, but the report and plan checkpoint are stale. Note that package and server versions remain `0.7.2`; `releaseForMigrationHead` will now label a pre-server-start 0071 database as `0.7.3` while the running version is `0.7.2`, contrary to the plan's “keep release surfaces at 0.7.2 during implementation.” Decide this with the release owner.
- `destination_key` is added without a default and set `NOT NULL` after the backfill. A rolling deploy with old 0.7.2 pods still inserting `audience_members` will get not-null failures until those pods are replaced; audience sync writes fail (loudly) during the overlap. Acceptable if migrations are coordinated, but worth an upgrade note.
- No test covers `removals=false` with an ordinary leaver whose identifiers change (the code path exists at `audiences.ts:384-393` and `:370-380`); the new test only covers consent refusal.
- No test asserts `ads.audiences` output for a platform removed from the artifact after cleanup succeeds (hidden) versus cleanup owed (shown). The new test covers the owed case only.

## 11. Missing tests (exact scenarios)

1. **Identifier shrink end state:** model membership in the fake Meta/Google server; after `['email','phone'] → ['phone']`, assert the member is still present by phone (forces a second add, or a different upload strategy). Update `reconciliation.test.ts:26-29` and `v073…test.ts:289-300`.
2. **DB failure after confirmed remote add:** fake accepts POST; inject a failure into `insertMembers`; erase; run again; assert no untracked remote hash (or a durable pending intent is visible).
3. **DB failure after confirmed reconcile remove+add:** same for `updateReconciledHashes`; assert the new hash is not lost.
4. **Timeout after the provider applied an add/remove**, then identifiers change or the profile is erased before retry.
5. **Unpublish/delete:** add, unpublish, erase/withdraw; assert the obligation is visible and can be executed/acknowledged.
6. **Legacy >65,535 rows:** one orphan group; assert the sync does not throw, the state is honest, and other workspaces still run.
7. **Connection settings mutation:** Google `customerId` changed under a sync; assert the old account is not silently “cleaned” against the new one.
8. **Two syncs, same destination:** one removes a member the other still wants; assert the survivor is re-added or duplicate destinations are rejected.
9. **Identifier reassignment:** old hash moves to another profile; assert a removal for one does not strand the other.
10. **Merge:** two profiles with ledger rows; merge; assert the survivor remains in the remote audience and the merged-away obligation is closed.
11. **`removals=false` ordinary leaver identifier change.**
12. **Migration upgrade visibility:** `ads.audiences` immediately after 0071 shows the legacy unresolved count/status, before any run.
13. **Scheduler isolation:** one sync throws (e.g., bind-limit fixture); assert the round continues with other syncs.

## 12. What is good

- Provenance is keyed per connection + destination, and the migration does not guess a pre-0.7.3 destination.
- Legacy rows stay as explicit cleanup obligations; prior-destination cleanup happens before the replacement is populated.
- Consent refusal/erasure removal is independent of `removals: false`.
- Additions are filtered for a usable identifier before the cap, with a durable keyset cursor.
- The advisory lock serializes the same sync without HTTP inside the app transaction; the destination-change and in-flight-add tests are useful.
- Typechecks/package tests were reported passing; no server Vitest was run here by instruction.
