## F1 — resolved/disabled retries (resolved)

`packages/alerts/src/evaluate.ts:314-344` now selects alert events on
`notified @> '[{"status":"queued"}]' OR notified @> '[{"status":"failed","retryable":true}]'`
(`:316-318` and `:326`), independent of `alert_rules.enabled` and without looking at
`resolved_at`. It calls `reconcileAlertNotifications(..., { retry: true })`, which re-opens the same
`deliveries` row (`packages/alerts/src/notify.ts:270-275`) rather than inserting a new one. The
payload, `target_id`, and `idempotency_key` are untouched (`:137-167` only resets
status/attempts/next-attempt/lease/response fields and increments the counter), so a resolved
episode re-sends the original event body and no synthetic event is invented.

The ledger converges: first sweep re-opens → `queued`, `cycles: 2`; if the worker later completes
it, the next sweep records `sent`; if cycle 2 dies, the next sweep records
`failed, retryable: false, cycles: 2` and the event drops out of the selection set. The new
DB-backed test `packages/alerts/test/delivery-status.test.ts:164-189` covers exactly this
(resolved event, disabled rule, re-open, then `sent`). The 15-test alerts package run passes.

## F3 — atomic re-open (resolved)

`reopenAlertDelivery` (`notify.ts:137-167`) is a single `UPDATE ... WHERE id = ? AND status IN
('dead','failed') AND alert_retry_cycles < MAX-1 RETURNING ...`. A row that is `pending`, `running`,
`done` or already re-opened cannot be reset, so a competing worker/scheduler cannot resurrect a
completed delivery or reset an in-flight attempt. On a failed update, the `notifyWebhook` caller
re-reads the row and reports its actual state (`:228-243`) instead of the stale `pending`. Under
READ COMMITTED the losing `UPDATE` re-evaluates the predicate against the winner's committed row,
so the guard is real and not check-then-act.

## F4 — durable retry budget (resolved)

`packages/db/migrations/0073_ops_reliability.sql:40-41` adds
`deliveries.alert_retry_cycles integer NOT NULL DEFAULT 0`, mirrored in
`packages/db/src/schema.ts:979`. The budget lives on the outbox row, not the ledger, so the
missing-ledger case cannot re-arm it: `reopenAlertDelivery` requires `alert_retry_cycles < 1`
(i.e. one re-open, two cycles with `MAX_ALERT_DELIVERY_CYCLES = 2` at `notify.ts:100`) and
increments it atomically (`:150-156`). `notificationOf` derives `cycles` and `retryable` from that
counter (`:128-130`), and `reconcileAlertNotifications` does the same (`:293-301`), so
status/cycles/retryable stay truthful after re-open and after terminal exhaustion. The new test
`delivery-status.test.ts:143-152` proves one extra cycle then `failed, retryable: false` **without**
any ledger entry, and the package run passed on a freshly migrated disposable DB.

**Through the real worker:** `deliverDue` (`packages/integrations/src/deliveries.ts:180-201`)
claims the re-opened row (`status='pending'`, `attempts=0`, due now), increments `attempts` per
attempt, retries on the unchanged `WEBHOOK_BACKOFF` schedule, then sets `dead` for webhooks. It
never writes `alert_retry_cycles`, so the counter survives the cycle. Re-open resets `attempts`,
`lease_until`, `finished_at`, response fields and leaves the payload/idempotency key intact, which
is exactly what the worker needs.

## Cross-cutting checks

- **Counter/default through the worker:** verified (above); the migration default applies to
  existing rows, the entity insert omits the column and takes the default, and the worker never
  resets it.
- **Racing sweeps:** two replicas both call the guarded `UPDATE`; only one increments the counter,
  and the loser cannot reset the winner's `pending`/`done` row. A loser can, however, write a
  transient stale ledger — see limitation 1.
- **RLS/grants:** `migrations/0009_integrations.sql:81-92` (GRANT at `:89`) grants table-level
  `SELECT, INSERT, UPDATE, DELETE` on `deliveries` to `am_app` and forces RLS with
  `workspace_id = app.workspace_id`; the new column therefore needs no separate grant and the
  `UPDATE` runs under `withWorkspace` in both the sweep and the evaluator. The sweep's admin
  workspace enumeration is the documented RLS-bypassing owner pattern. `reopenAlertDelivery`
  omits an explicit `workspace_id` predicate and relies on RLS (limitation 6).
- **Helper types/callers:** `reconcileAlertNotifications`'s new `{ retry?: boolean }` keeps the two
  existing evaluator call sites unchanged (`evaluate.ts:250,289`), and the reopen helper's return
  type is consistent with `notificationOf`. `_previous` is now dead (limitation 4).
- **Truthfulness:** `queued`/`sent`/`failed` follow `deliveryNotificationStatus`
  (`notify.ts:103-107`); `failed` carries the delivery error, `cycles` reflects the current row
  cycle, and `retryable` is `false` exactly when the counter has used its one re-open. Missing
  ledger rows are made terminal (`:281-291`).
- **No unrelated OAuth baseline review** was needed; the delta touches no integration file.

## Remaining limitations (all non-blocking)

1. **P3 — sweep CAS loser does not re-read.** In `reconcileAlertNotifications` the retry loop uses
   `(await reopenAlertDelivery(tx, row.id)) ?? row` (`notify.ts:270-275`); the `?? row` fallback is
   the stale `dead`/`failed` snapshot. Unlike `notifyWebhook` (`:228-243`), it does not re-read the
   row after a failed CAS. With two scheduler replicas, the loser can transiently persist
   `failed, retryable: true` while the winner's row is actually `pending`/`done`. The next
   5-minute sweep (see `runAlertEvaluator`, `evaluate.ts:372-377`) rewrites it to `queued`/`sent`,
   and the re-open/terminal decision is still made from the row counter, so no extra cycle or lost
   delivery results. Cheap fix: on a missing `UPDATE` return, `SELECT` the row and use that state
   (same as `notifyWebhook`).
2. **P3 — upgrade overrun of the budget.** Because `alert_retry_cycles` defaults to `0`, a delivery
   that had already used its one legacy re-open (`notified[].cycles = 1`, terminal) before this
   deploy gets one fresh cycle (up to the worker's ~17 h schedule) after upgrade. It is bounded to
   one extra cycle per row and cannot repeat. Related deployment note: the column was added by
   editing the still-unreleased `0073` file rather than adding `0074`; the server test template is
   recreated per run (`apps/server/test/harness.ts:161-176`), and production `0.7.3` has not seen
   `0073` (`origin/main` stops at `0071`), so only a manually persisted DB migrated at `2de1865`
   would need a fresh migration or manual `ALTER`.
3. **P3 — `notifyWebhook`'s disappeared-row branch still promises a retry.** `notify.ts:213-222`
   returns `status: 'failed', retryable: true` with **no** `deliveryId` when the conflicting row is
   not visible on re-select. If that ever happens (row deleted between `onConflictDoNothing` and
   the select), `reconcileAlertNotifications` returns early because `ids` is empty, so the sweep
   selects that event every tick and can never terminalise it. It is effectively unreachable (the
   insert/select are in one transaction), and no 0.7.3 ledger has `retryable` without a
   `deliveryId`; still, it is the one spot where the resolution doc's "missing payloads are
   terminal" is not literally true. Consider returning `retryable: false` or letting the sweep
   terminalise entries with no `deliveryId`.
4. **P4 — dead helper parameter and a stale type comment.** `notificationOf`'s `_previous`
   parameter (`notify.ts:116`) is no longer read by any branch while callers still pass
   `existing`; remove it or use it. `AlertNotification.cycles`'s comment
   (`packages/db/src/schema.ts:1110`) says "completed outbox cycles", but the value is now the
   1-based current cycle (1 initially, 2 after the re-open, 2 at terminal). Behaviour and tests are
   consistent; only the comment is misleading.
5. **P4 — test/diagnostic nits.** The bulk-enroll test still includes the old duplicate query
   (`:294-302`), which alone cannot catch a cursor regression (the entry-key index absorbs a
   re-scan); the new cursor/count/participant assertions are what make it meaningful. The flaky
   wrapper also fails whichever workspace job is due first; if a future test leaves an earlier
   queued job, the retry test fails loudly (`attempts: 1`/`error` assertions) rather than passing
   silently. The `MAX_ALERT_DELIVERY_CYCLES` comment says "seven attempts"; the worker actually
   allows eight (`attempts` is incremented on claim, `d.attempts > backoff.length` with a 7-entry
   backoff) — pre-existing.
6. **P4 — RLS-only scoping.** `reopenAlertDelivery` filters by delivery `id` only. Production is
   safe because `deliveries` is `FORCE ROW LEVEL SECURITY` and `am_app` has table-level `UPDATE`;
   the disposable/package tests connect as the owner role, so they cannot catch a missing policy or
   grant. Adding `workspace_id = ?` would be defence in depth (the prior review made the same
   note for the sweep query).
7. **P4 — late firing payload after resolution (by design).** A resolved episode whose *firing*
   delivery died is re-opened with its original `alert.firing` payload; no `alert.resolved` is
   synthesised. This is exactly what the resolution doc promises, but consumers can receive a late
   firing webhook after the metric recovered; worth one line in the upgrade notes.
