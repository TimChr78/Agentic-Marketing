- The idempotency contract is now documented and implemented by the shipped clients. `docs/integrations.md`, the architecture overview and the generated OpenAPI route descriptions explain that a key is remembered for the life of the workspace, that reusing it for another command, input or caller answers `409` with `details.reason: "idempotency_key_reused"`, and that a `409` with `"idempotency_in_progress"` means the first request is still running: retry with the same key, never a new one.
- An idempotency key is scoped to its caller as well as its workspace: a person's user id across sessions, or one agent record (each API token and OAuth connection is its own agent). A different caller presenting the same key answers `409 idempotency_key_reused` and never receives the first caller's stored response. Rows written before 0.14.24 carry the old caller-agnostic hash, so a retry that spans the upgrade answers `409`; use a new key. An empty or malformed key (more than 200 characters, a space or a non-printable character) is refused with `400 invalid_input` on every surface instead of being treated as "no key", so it cannot silently run twice.
- MCP write tools accept an optional `idempotencyKey` argument (1–200 printable characters, no spaces); it is passed to the executor and is not part of the command's own input. Tools whose input already has an `idempotencyKey` (a send, a bulk enrollment) keep that field's meaning. Read tools are unchanged.
- The typed client exports `callWithRetry`, which mints one key per logical call and retries a network failure or an in-progress conflict with the same key (five attempts, about 12 seconds), and never retries the reused-key conflict or another 4xx. `conflictReason` and `isIdempotencyInProgress` are exported for custom loops.
