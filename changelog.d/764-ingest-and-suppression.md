- Connector webhooks (Shopify, Salesforce and a generic mapping) no longer run the workspace tracking plan, so a strict plan cannot silently drop a mapped order or record while the sender is told the delivery succeeded. Senders see no status-code change: accepted deliveries still answer 200, and a replay is still a 200 that says nothing new was ingested.
- Replay protection now covers every inbound connection, not only Standard Webhooks. A byte-identical body on an `hmac-sha256` or unsigned generic webhook is answered as already received and publishes nothing; a different body publishes again. Those schemes carry no timestamp, so the dedupe window is the hot-state TTL (10 minutes). The identity is the body plus the headers the mapping uses: one that names headers statically (`headers.x`, `headers."x-name"`, `headers.` + a backquoted name, or `$lookup(headers, "x-name")`) contributes exactly those headers, while any other use of `headers` (`$keys(headers)`, `$each`, `$sift`, `headers[...]`, a computed `$lookup` name, passing `headers` wholesale, `$`/`$$` context access or `$eval`) contributes every header. The mapping is read through JSONata's parser, so comments and escaped names cannot hide a header read. With a dynamic mapping, a sender retry that changes a per-attempt header (`x-request-id`, `date`, a trace id, `cf-ray`, the Standard Webhooks timestamp and signature) therefore counts as a new event; map the headers you read by name, or use Standard Webhooks, whose signed `webhook-id` is the replay key whatever the mapping does. The Shopify topic is always part of the identity, so an order delivered as both `orders/create` and `orders/paid` records both.
- A hard bounce or complaint that arrives while an SMS STOP suppression already holds the number now escalates the row instead of being dropped, so a later START cannot unsuppress a number that bounced or complained.
