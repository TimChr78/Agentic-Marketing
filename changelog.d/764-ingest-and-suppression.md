- Connector webhooks (Shopify, Salesforce and a generic mapping) no longer run the workspace tracking plan, so a strict plan cannot silently drop a mapped order or record while the sender is told the delivery succeeded. Senders see no status-code change: accepted deliveries still answer 200, and a replay is still a 200 that says nothing new was ingested.
- Replay protection now covers every inbound connection, not only Standard Webhooks. A byte-identical body on an `hmac-sha256` or unsigned generic webhook is answered as already received and publishes nothing; a different body publishes again. Those schemes carry no timestamp, so the dedupe window is the hot-state TTL (10 minutes). The identity is the body plus every request header except the per-attempt ones (`date`, request and trace ids, client-IP and forwarding headers, `user-agent`, the Standard Webhooks timestamp and signature) that the mapping did not read when it ran, however the expression reached them. Deliveries whose mapped events differ never share an identity, whatever the mapping does with time or randomness, and an ordinary sender retry still dedupes; a mapping that reads a per-attempt header treats a retry that changes it as a new delivery, so use Standard Webhooks, whose signed `webhook-id` is the replay key whatever the mapping does, if you need such headers. The Shopify topic is always part of the identity, so an order delivered as both `orders/create` and `orders/paid` records both.
- A hard bounce or complaint that arrives while an SMS STOP suppression already holds the number now escalates the row instead of being dropped, so a later START cannot unsuppress a number that bounced or complained.
