- Activates the 0.17.0 erasure completion contract (#1037, part 3 of 3). Once `profiles.erasureStatus` reports `complete`, every application query started afterwards excludes the erased subject and its contribution to newly computed analytics, including rows written after completion; physical deletion is a separate, eventual milestone. `complete` now requires the erasure's ledger to be published to `erased_subjects` and confirmed visible, and the workspace's subject-key coverage count to be zero, so no person-linked row remains that a protected read cannot check. Until then the status reports a `reason` (`publication`, `outbox`, `final_sweep` or `subject_key_coverage`), and the SQL completion refuses the same gate. `profiles.erasureStatus` gains `exclusion` (`full` or `partial`), `unavailableKinds` (an e-mail/phone plaintext that could not be recovered, reported instead of claimed as excluded) and `purge: { state, lastSweepAt, deletedRows }`; existing fields are unchanged. A recurring scheduler job physically sweeps `events`, `message_events` and `journey_events` for rows matching the retained exclusion keys in bounded batches, using the same keyed matching as protected reads (including `events.profile_id`), never deleting the ledger or published exclusions, and keeps re-sweeping because late writes can still arrive. `am doctor` reports exclusion coverage (`privacy.erasureExclusion`) and the physical-purge backlog (`queue.erasurePurge`) separately; an empty cleanup queue alone is not evidence. **Manual step (drained upgrade):** this is a drained upgrade like #978: stop old workers with write access before starting 0.17.0, because an old writer does not fill subject-key coverage. The historical subject-key backfill must reach zero uncovered rows before erasures can complete; leave the scheduler role running and watch `clickhouse.subject-keys` and `queue.erasurePurge` in `am doctor`. How long the backfill takes depends on the number of stored events, message events and journey events; a large install should expect one pass per partition batch, with revalidation afterwards. The exclusion key is long-lived and must be kept with its ledger: a compromised key is replaced for new writes only, and old entries remain excluded under the retained versions.
